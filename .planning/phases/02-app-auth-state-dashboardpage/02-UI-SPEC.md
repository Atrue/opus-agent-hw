## Interaction Contract

This phase's UI work is interaction, not visuals. Locked behavior:

| Interaction | Contract | Source |
|-------------|----------|--------|
| Valid submit on login | Form disappears (LoginPage unmounts), dashboard renders with `h1` «Дашборд» and the email line. No transition/animation. | D-01, D-02, AUTH-02 |
| «Выйти» click | `type="button"`, calls `onLogout` → `setUser(null)` → `LoginPage` remounts with empty fields and no error. No confirmation step. | D-03, D-04, AUTH-03 |
| Re-login after logout | Works identically to first login — no stale state anywhere (no persistence by design). | ROADMAP Phase 2 criterion 3 |
| Page switching mechanism | Conditional render in `App.jsx` only (`user ? <DashboardPage/> : <LoginPage/>`). No router, no `window.location`, no scroll/URL side effects. | D-06, success criterion 4 |
| Invalid submit on login | Unchanged from Phase 1: form-level `<p role="alert">` «Заполните email и пароль»; error state never leaves `LoginPage`. | D-05 |
| Reload | Returns to login page (in-memory state lost) — intended, not a bug. | Out of Scope: persistence |

**Accessibility contract (carried from LoginPage pattern):**
- One `<h1>` per page; `<main className="<page>-page">` wrapper (`dashboard-page` mirrors `login-page` — discretion item resolved to follow the established pattern).
- Buttons are real `<button>` elements with accessible names exactly matching the copy above.
- Form labels keep `htmlFor` + `id` wiring; `type="email"` / `type="password"` / `autoComplete` attributes unchanged.
- Error messaging stays `<p role="alert">` (no `alert()` — already banned project-wide).
