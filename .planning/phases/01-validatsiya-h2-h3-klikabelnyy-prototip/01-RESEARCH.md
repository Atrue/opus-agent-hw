## Summary

Фаза состоит из трёх ортогональных работ, которые почти не зависят друг друга и могут идти параллельно: (1) H2 — 5 проблем-интервью с преподавателями по методике Mom Test: спрашиваем про прошлое и текущую практику объяснения backprop, не питчим; «≥2 согласия на пилот» считается честно только как commitment level 2 (названный курс + срок + принятый конкретный следующий шаг с датой), вежливые «да, интересно» не считаются. (2) H3 — think-aloud юзабилити-тест кликабельного прототипа XOR-walkthrough на 5–8 студентах 1–2 курса, удалённо с записью экрана; completion считается как unassisted-дихотомия, для каждого N заранее известно минимальное число завершивших (N=5→4, N=8→5), чтобы критерий «>60%» не считался постфактум в пользу автора. (3) Прототип — первый срез реального UI-плеера по паттерну ARCHITECTURE.md «мок-trace + чистый плеер (trace, stepIndex)»: Vite 8 + React 19 + TS strict + Tailwind 4 + Zustand, числа из offline-прогона чистым Python (stdlib-only, micrograd-семантика, фикс. seed, явные веса в JSON) — это же формат прообраза golden-фикстур Phase 2.

Ключевые расчётные решения, снятые этим исследованием: сеть прототипа **2-3-1** (tanh-скрытый, sigmoid-выход, BCE), полный цикл на **одном сэмпле XOR = 14 шагов** (7 forward вкл. loss + 5 backward + 1 update + 1 финальная сводка) — достаточно длинно, чтобы поймать усталость и «плоский счётчик», достаточно коротко для 30–40-минутной сессии; лекционный кегль — toggle ×2 (28–32px числа) одним CSS-классом; формулы в прототипе — Unicode-строки в mono-шрифте (KaTeX отложен в Phase 2 без переписывания плеера); URL-состояние шага — hash (`#step=N`), без react-router в Phase 1. Автоматизируемая часть верификации — один Playwright-смок (~5 проверок: полный проход до сводки без NaN, шаг назад, reload восстанавливает шаг, drill-down, «шаг N из M») + несколько Vitest-юнитов (urlState, store-границы, sanity мок-JSON); всё человеческое (интервью, think-aloud, «найти число <10 сек») — ручной протокол с записью и шаблоном в EVIDENCE.md.

**Primary recommendation:** Планировать фазу тремя параллельными треками — (A) гайд+скрининг+проведение H2-интервью двумя волнами (первые 2–3 чисто проблемные, после сборки прототипа следующие 2–3 с 2-минутным демо в финальном блоке для честного commitment-aska), (B) генератор мок-трейса → (C) скелет плеера, затем юзабилити H3, DESIGN-TOKENS.md и формальный go/no-go по правилу D-07.

## Research Question 1: Mom Test интервью (H2)

### 1.1 Ядро методики (что фиксирует валидность)

Mom Test (Rob Fitzpatrick, «The Mom Test», 2013) `[ASSUMED — стабильная, широко воспроизводимая методика; книга неизменна с 2013]`, практическая уверенность HIGH:

- **Спрашивать про жизнь респондента, не про идею.** Вопросы о прошлом и текущей практике («расскажите про последний раз, когда вы объясняли backprop»), не о будущем и не о нашем продукте.
- **Конкретика в прошлом > мнения о будущем.** Всё, что «would you / стали бы вы», — мусор: люди вежливо лгут, чтобы не обидеть. Ценность имеют только факты о поведении и понесённых издержках.
- **Комплименты = красный флаг.** «Круто!», «отличная идея» — сигнал, что интервью провалено в этой точке; единственная валюта — факты + commitments (обязательства с издержками).
- **Правило большого пальца:** каждое свидетельство боли должно опираться на прошлый эпизод, а не на гипотетическое «студентам обычно сложно».

Проверка каждого вопроса гайда: «узнаю ли я из ответа факт о его жизни/курсе, или обещание/вежливость?» Если второе — переформулировать.

### 1.3 Commitment-лестница и честный подсчёт «≥2 на пилот»

Определить **до** первых интервью и не двигать потом `[рекомендация research;acked D-04 требует явного согласия/несогласия]`:

| Уровень | Что это | Считается в «≥2»? |
|---|---|---|
| 0 | Вежливый интерес: «звучит полезно», «пришлите, посмотрим» | **Нет** |
| 1 | Слабое обязательство: согласился на конкретный следующий шаг (посмотреть прототип к дате; показать коллеге/завкафедрой) | **Нет** (но логируется) |
| 2 | **Пилотное обязательство**: назван курс/группа + срок («на лабе в весеннем семестре») + принят следующий шаг с датой и владельцем (созвон на следующей неделе / «пришлите к 15-му, я поставлю в расписание») | **Да** |

Mom Test-принцип: обещания ценны только еслиcostят респонденту времени/репутации. Go-критерий H2 = **≥2 интервью с уровнем 2**. Правило записи: уровень 2 валиден только с дословной цитатой + конкретикой (что, когда, кто делает) — иначе деградирует до уровня 1.

### 1.4 Скрининг респондентов (H2)

Включающие критерии (все обязательны):
- Преподаёт курс с backprop в программе (ML/DL intro, «нейронные сети») — вуз или буткемп;
- Провёл ≥1 лекцию/семинар с объяснением backprop за последние 2 года (иначе «расскажите про последний раз» пуст);
- Не близкий друг/коллега автора (вежливое смещение — главный биас Mom Test).

Желательная вариативность: 1–2 исследовательских вуза, 1 региональный, 1 буткемп/магистратура — разные условия (проекторы, LMS, доступность техники).

Каналы (discretion): TG-сообщества преподавателей ML, ODS-контакты, кафедральные чаты; после каждого интервью — реферал (блок 5). Скин-сообщение: «исследую, как преподают backprop, 40 минут, никуда не продаю, результаты анонимно».

### 1.5 Типичные ошибки problem-interview (чек-лист против них)

- **Питчинг** (рассказали про продукт в начале) → респондент переключается в режим оценки идеи → фактов о боли больше не будет. Против: концепт только в блоке 4.
- **Гипотетические вопросы** («пользовались бы вы…?», «сколько бы заплатили?») → вежливая ложь. Против: только «расскажите про случай, когда…».
- **Наводящие** («не кажется ли вам, что студентам сложно с градиентами?») → респондент соглашается из вежливости. Против: открытые «что студентам даётся тяжелее всего на этой теме?».
- **Принятие комплиментов за сигнал** → спросить «а что смущает?» сразу после похвалы.
- **Говорить >20% времени** → тайм-бок блоков, вопросы коротко.
- **Не фиксировать дословные цитаты** → без цитат EVIDENCE-запись вырождается в мнения автора; писать/записывать verbatim.
- **Смешивать сегменты** (спрашивать преподавателей про боли студентов как главный факт) → боль студента = отдельный H3-протокол.

## Research Question 2: Юзабилити-протокол H3 (think-aloud, 5–8 студентов)

### 2.1 Формат

- **Moderated remote think-aloud, 1-на-1, 30–45 мин**, запись экрана+звука с явным согласием на запись (озвучивается на записи). Zoom/Meet/любой инструмент со шарингом экрана `[ASSUMED — устойчивая практика; конкретный инструмент неважен]`.
- Think-aloud: «выполняй задачу и проговаривай вслух всё, что видишь и думаешь»; модератор напоминает «продолжай говорить», но **не объясняет интерфейс и не помогает** до конца задания. Классический протокол: Ericsson & Simon / Nielsen «Thinking Aloud: The #1 Usability Tool» `[ASSUMED, уверенность HIGH — канон методики]`.
- N=5–8 — формирующий (formative) размер: классическая оценка Nielsen/Landauer «5 пользователей находят ~85% проблем юзабилити» `[ASSUMED — канон; сам же критерий H3 (completion > 60%) дихотомичен, поэтому трактуем по правилу ниже, а не статистически]`.
- **Сухой прогон протокола на 1 знакомом (не в счёт)** — калибрует тайминги и скрипт до реальных респондентов.

### 2.2 Скрининг респондентов (H3)

- Студент 1–2 курса CS/DS (или эквивалент самоучки ДО первого касания autodiff — «впервые проходящие backprop» по D-05);

Скин: 3–4 вопроса (курс? проходил ли backprop? писал ли autodiff сам? устройство?). Рекрутинг: те же каналы, что H2 (студенческие чаты курсов, TG-сообщества; рефералы от первых респондентов).

### 2.3 Задания (по D-05, дословно в протокол)

1. **Дойти до конца walkthrough.** Инструкция: «Открой ссылку. Пройди сценарий до конца, шаг за шагом, проговаривая вслух. Не спеши.» Метрики: дошёл/нет (unassisted), шаг и цитата тупика, суммарное время, моменты непонимания (шаг + цитата из think-aloud).
2. **Вернуться на шаг назад.** «Вернись на один шаг назад и покажи, что там было.» Метрика: нашёл ли kontrol/клавишу сам; время.
3. **Найти число.** «Чему равен градиент веса W₁[2,1] на текущем шаге?» (число выбрать из текущего видимого шага; задание одинаковое для всех — указать в протоколе конкретное). Метрика: время от конца инструкции до вербального ответа/указания пальцем по записи; порог < 10 сек — по записи экрана (specifics из CONTEXT.md).
4. Пост-мини-интервью (5 мин): «объясни своими словами, откуда взялся вот этот градиент» (1 вопрос на понимание backward — качественный сигнал, НЕ критерий); «что было самым непонятным?»; «если бы показывал это преподаватель на лекции — тебе было бы видно с задних рядов?» (дешёвая калибровка DOCS-05); самооценка сложности 1–7; вопрос про нотацию — считается каждый спонтанный вопрос «а что это обозначение значит» (Pitfall 13 индикатор).

### 2.4 Правило подсчёта completion > 60% (зафиксировать ДО теста)

Completion = **бинарный факт: респондент дошёл до финальной сводки без подсказок по механике продукта**. Разрешённые вмешательства модератора: «продолжай говорить вслух», «расскажи, что ты сейчас видишь». Любая помощь «как пройти/где нажать» = assisted completion (фиксируется, но не считается). Формирующая таблица минимальных прохождений `[арифметика, не требует источника]`:

| N респондентов | Минимум completions для >60% | Фактический порог |
|---|---|---|
| 5 | 4 | 80% (3/5 = 60% — не > 60%) |
| 6 | 4 | 66.7% |
| 7 | 5 | 71.4% (4/7 = 57.1% — нет) |
| 8 | 5 | 62.5% |

Плюс к completion: время поиска числа (медиана/макс по записям), число тупиков, список шагов с моментами непонимания (для редизайна до Phase 2).

### 2.5 Сколько шагов/экранов должен иметь прототип

Расчёт (см. RQ3/RQ4): один полный цикл XOR на одном сэмпле = **M = 14 шагов** (7 forward вкл. loss, 5 backward, 1 update, 1 сводка). Сравнение с ориентирами: FEATURES.md оценивает «XOR на 2-2-1 ≈ 20–30 ops» `[VERIFIED: .planning/research/FEATURES.md:58 — «XOR on a 2-2-1 net ≈ 20–30 ops»]` — 14 шагов ниже, потому что (а) backward-матvec считается одной op с несколькими выходами-градиентами (зеркалирует forward один-к-одному, ARCHITECTURE.md §1), (б) walkthrough = один сэмпл. Этого достаточно для H3, потому что:
- главный риск H3 — понятность **backward** (D-02) — полностью покрыт (5 backward-шагов + update);
- усталость/маршрут («плоский счётчик» — PITFALLS UX-таблица) видны уже на 10+ однотипных шагах;
- сессия укладывается в 30–40 мин: 14 шагов × 40–60 сек think-aloud ≈ 10–15 мин + задания 2–3 + пост-интервью.
Один экран (диаграмма + панель шага + нарратив + контролы) + drill-down-панель как второй «экран». Больше экранов/роутов прототипу не нужно.

Если на сухом прогоне время превысит 45 мин — сокращать нарратив, а не шаги (шаги = объект теста).

### 2.6 Валидность и смещения (что прописать в протоколе)

- **Автор-модератор** — главный биас (вежливость к автору). Митигируется жёстким скриптом: ни одного оценочного слова («мы сделали», «понятно ли вам?» запрещены; только «что вы видите?», «расскажите, что сейчас происходит»). Идеал — нейтральный модератор; реалистично для одного автора — скрипт + сухой прогон.
- **Загрязнение нотацией**: модератор НЕ объясняет обозначения до заданий — спонтанные вопросы «а что это δ/∂?» логируются как данные (Pitfall 13).
- **Порядковый эффект**: задание 1 всегда первое (главное); задания 2–3 на фиксированном шаге протокола (например, шаг 8) — одинаковые условия для всех.
- **Запись согласия** — на записи, в начале; данные в EVIDENCE.md анонимны (псевдоним, курс).
- Технический аудит сессии: попросить респондента открыть ссылку в инкогнито (чистое состояние), fullscreen off, разрешение записи экрана — чек-лист в начале протокола.

## Research Question 3: Мок-данные — offline-генерация правдоподобного walkthrough XOR

### 3.1 Жёсткое окруженческое ограничение (проверено в сессии)

`[VERIFIED: bash-проверка этой сессии]` На машине автора: **Python 3.9.6, torch и numpy НЕ установлены** (`torch NOT installed`, `numpy NOT installed`). Значит генератор обязан быть **stdlib-only** (math/random/json). Это не проблема, а уточнение выбора: micrograd — референс NFR-02 — сам по себе stdlib-only (`engine.py` использует только `math`/`random`) `[ASSUMED — устойчивое знание репозитория karpathy/micrograd; проверить при вендоринге]`. PyTorch для мок-фазы не нужен вовсе — он понадобится в Phase 2 для golden-фикстур на тех же весах.

### 3.2 Что генерировать: сеть, сэмпл, шаги

**Сеть (discretion из CONTEXT.md — рекомендация):** MLP **2-3-1** — 2 входа, 1 скрытый слой из 3 tanh-нейронов, 1 sigmoid-выход, лосс BCE, SGD lr=0.5. Обоснование: ровно пример из ARCHITECTURE.md (`fanIn 2 → fanOut 3`, `loss: bce`, `lr: 0.5`) `[VERIFIED: .planning/research/ARCHITECTURE.md:121-127 — цитата конфига сценария]`; меньше чисел, чем 2-4-1 → меньше риск «стены цифр» на прототипе; drill-down остаётся содержательным (W₁ — матрица 3×2). Forward один сэмпл (например, x=[1,0], y=1).

**Гранулярность шагов (D-02 «op-гранулярность») — итоговый список M=14:**

| # | phase | op | формула (нотация D-06) |
|---|---|---|---|
| 1 | forward | matvec | `z₁ = W₁·x` |
| 2 | forward | add | `z₁ = z₁ + b₁` |
| 3 | forward | tanh | `a₁ = tanh(z₁)` |
| 4 | forward | matvec | `z₂ = W₂·a₁` |
| 5 | forward | add | `z₂ = z₂ + b₂` |
| 6 | forward | sigmoid | `ŷ = σ(z₂)` |
| 7 | loss | bce | `L = −[y·ln ŷ + (1−y)·ln(1−ŷ)]` |
| 8 | backward | bce-grad | `∂L/∂ŷ = −(y−ŷ)/(ŷ(1−ŷ))` (значение = (ŷ−y)/(ŷ(1−ŷ)) по знаку — сгенерирует скрипт) |
| 9 | backward | sigmoid-grad | `∂L/∂z₂ = ∂L/∂ŷ · ŷ(1−ŷ)` |
| 10 | backward | matvec-grad | `∂L/∂W₂ = ∂L/∂z₂ · a₁ᵀ`, `∂L/∂b₂ = ∂L/∂z₂`, `∂L/∂a₁ = W₂ᵀ·∂L/∂z₂` |
| 11 | backward | tanh-grad | `∂L/∂z₁ = ∂L/∂a₁ ⊙ (1−a₁²)` |
| 12 | backward | matvec-grad | `∂L/∂W₁`, `∂L/∂b₁`, `∂L/∂x` — граница графа: «∂L/∂x — вход, старт цепного правила» (DOCS-02 edge case прямо в прототипе) |
| 13 | update | sgd | `W ← W − η·∂L/∂W` (показать один вес явно, остальные сводкой — «паттернный шаг», PITFALLS 12) |
| 14 | summary | — | сводка: L до/после, ‖grad‖, «что дальше» (микро-DRAMатургия завершения — DOCS-01 edge case) |

Прим.: шаг 8 при желании объединяется с 9 (fused) — решение фиксируется в generator-скрипте комментарием; выбранная декомпозиция должна совпадать с Phase 2 (Pitfall 4 «дидактическая декомпозиция vs эталон»). BCE-декомпозиция в прототипе безопасна: веса подбираются «спокойные» (см. 3.4), ŷ не уходит к 0/1.

### 3.3 Детерминизм: seed → явные веса → коммит

- Веса генерируются `random.Random(42)` (stdlib, детерминирован) один раз; **сгенерированные числа коммитятся в JSON как явные данные** (поля `weights`) — далее JSON самодостаточен и воспроизводим без Python. Это ровно принцип ARCHITECTURE.md: «Initial weights are explicit data, not generated» `[VERIFIED: .planning/research/ARCHITECTURE.md:140-142]`.
- Регенерация byte-stable: скрипт пишет JSON с фиксированными `sort_keys=False, separators=(', ', ': ')`, без timestamp-полей (либо константа) — `gen && git diff --exit-code` как микро-CI (прообраз Phase 2-дисциплины) `[VERIFIED: .planning/research/ARCHITECTURE.md:197 — «committed fixtures … CI check that regeneration is byte-stable»]`.
- Точность чисел: Python `json.dump` пишет float через repr = shortest round-trip; JS `JSON.parse` восстанавливает тот же double bit-exact `[CITED: .planning/research/STACK.md — раздел Testing Stack фиксирует этот механизм]`. **Не округлять** числа в JSON — форматирование только в UI (d3-format).

### 3.4 Педагогический санити-фильтр весов (важно для валидности теста)

Сгенерировать seed → проверить условия → если не проходит, инкрементировать seed и повторить (в том же скрипте, автоматически):
- начальный L ∈ [0.4, 1.0] (не «уже угадал», не экстремум);
- все |pre-tanh| < 2.5 и |pre-sigmoid| < 2.5 (нет насыщения — Pitfall 4);
- веса в диапазоне ~±1 (читаемы на диаграмме и в таблице);
- градиенты первого слоя не вырождены (|∂L/∂W₁| > 1e-4 — чтобы числа были «живые»).
Выбранный seed записать в JSON (`"seed": 42`) — Pitfall 4: «XOR-сценарий со спокойными весами» `[VERIFIED: .planning/research/PITFALLS.md:88]`.

### 3.5 Самопроверка генератора: gradcheck внутри скрипта

Скрипт после построения трейса считает central-difference проверку каждого аналитического градиента (h≈1e-6, допуск rel 1e-4 — предел конечных разностей) и **падает**, если расходится; в JSON пишется `"gradCheck": {"method": "central-difference", "maxRelErr": <факт>}`. Это ~30 строк и прямой прообраз методологии Phase 2 `[CITED: .planning/research/ARCHITECTURE.md §6 — gradcheck «что делает движок тестируемым с первого дня»]` + `[CITED: pytorch autograd.gradcheck — методология; из STACK.md Sources]`.

### 4.4 Zustand store (эскиз кода)

```ts
// src/player/store.ts
import { create } from 'zustand';
import trace from '../data/xor-trace.json';
import type { TraceStep } from './types';

type Mode = 'default' | 'lecture';
type Drill = { kind: 'number'; stepIndex: number; ref: string } | null;

interface PlayerState {
  stepIndex: number;
  drill: Drill;
  mode: Mode;
  next: () => void;             // на последнем шаге — no-op (сводка и есть финал)
  prev: () => void;             // шаг назад бесплатен: stepIndex-1
  jumpTo: (i: number) => void;
  openDrill: (ref: string) => void;
  closeDrill: () => void;
  toggleMode: () => void;
}

export const usePlayer = create<PlayerState>((set, get) => ({
  stepIndex: 0,
  drill: null,
  mode: 'default',
  next: () => set((s) => ({ stepIndex: Math.min(s.stepIndex + 1, trace.steps.length - 1), drill: null })),
  prev: () => set((s) => ({ stepIndex: Math.max(s.stepIndex - 1, 0), drill: null })),
  jumpTo: (i) => set({ stepIndex: Math.min(Math.max(i, 0), trace.steps.length - 1), drill: null }),
  openDrill: (ref) => set({ drill: { kind: 'number', stepIndex: get().stepIndex, ref } }),
  closeDrill: () => set({ drill: null }),
  toggleMode: () => set((s) => ({ mode: s.mode === 'default' ? 'lecture' : 'default' })),
}));

// selectors (derived, не хранятся)
export const selectStep = (s: PlayerState): TraceStep => trace.steps[s.stepIndex];
export const selectPosition = (s: PlayerState) => `${s.stepIndex + 1} / ${trace.steps.length}`;
```

Синхронизация URL — подписка в App: `usePlayer.subscribe` → `location.hash = `step=${i}${mode==='lecture' ? '&mode=lecture' : ''}`` через `history.replaceState` (без засорения истории; reload-restore — чтение hash при старте). Клавиатура — один `keydown`-listener (Space/ArrowRight → next, ArrowLeft → prev).

**Правило из ARCHITECTURE.md, которое прототип обязан соблюдать с первого дня:** UI — чистая функция над `(trace, stepIndex)`; никакие числа не считаются в компонентах (только форматирование) `[CITED: .planning/research/ARCHITECTURE.md — Pattern 1 + Data Flow]`.

### 6.2 Playwright-смок (e2e/smoke.spec.ts, 5 проверок)

## Common Pitfalls

### Pitfall 1: Вежливое «да» вместо пилотного обязательства (H2)
**What goes wrong:** считают «отличная идея, пришлите» как согласие → ложный H2-go.
**How to avoid:** commitment-лестница §1.3; уровень 2 только с цитатой+конкретикой; правило зафиксировано в гайде до интервью.
**Warning signs:** в EVIDENCE.md записи без verbatim-цитат; все 5 согласны «посмотреть» (подозрительно однородно).

### Pitfall 2: Питчинг в первых минутах интервью
См. §1.5. Против: тайм-боксы; концепт/демо только в блоке 4, у волны A — вообще без демо.

### Pitfall 3: Загрязнение юзабилити-сессии объяснениями модератора
**What goes wrong:** модератор объясняет нотацию/навигацию «чтобы не мучить» → респондент проходит, H3-green ложный.
**How to avoid:** скрипт §2.6; помощь только ПОСЛЕ задания (фиксируется как assisted); спонтанные вопросы по нотации — данные, а не повод помогать.

### Pitfall 4: Стена цифр в дефолтном виде шага
`[VERIFIED: .planning/research/PITFALLS.md §5]` 3–7 чисел по умолчанию; подсветка изменившегося; задание 3 (найти число <10 сек) — калибрует. >30 чисел одновременно на экране прототипа — красный флаг до теста (самопроверка скриншотом).

### Pitfall 5: Ручные «правдоподобные» числа в JSON
D-03 запрещает явно. Против: числа только из генератора; trace-sanity-тест ругается на ручные правки (schema/coverage); git blame покажет источник.

### Pitfall 6: Scope creep прототипа (KaTeX/роутер/PWA/мобильный/движок)
AF-паттерн из FEATURES (Pitfall 8 PITFALLS). Против: таблица §4.1 «включаем/откладываем» — план ссылается на неё; каждое добавление обосновывается критерием фазы.

### Pitfall 7: Состояние шага только в memory/localStorage → reload-провал
Specifics фазы требует URL-state. Против: hash `#step=N` (§4.4); e2e-проверка №4.

### Pitfall 8: Смешение нотаций (∂L/∂W vs δ vs dL/dW)
`[VERIFIED: .planning/research/PITFALLS.md §13]` Одна нотация из D-06 во ВСЕХ строках (генератор + UI-хром); счётчик вопросов «что это обозначение» в H3-протоколе.

### Pitfall 9: Переинтерпретация small-N
5–8 — формирующая выборка; completion-критерий дихотомичен по правилу §2.4, но каверзные выводы («студенты понимают chain rule») делаются только цитатами, не процентами.

### Pitfall 10: Float-форматирование в JSON (округление «для красоты»)
Ломает round-trip и прообраз NFR-02. Против: полный repr в JSON (§3.3); форматирование только наdisplay-слое.

### Pitfall 11: Недетерминированная регенерация мок-трейса
Скрипт без фиксированных separators/порядка → git diff шумит, «фикстуры свежие»-дисциплина Phase 2 ломается на старте. Против: §3.3 byte-stable правила + `gen && git diff --exit-code` в чек-листе фазы.

### Pitfall 12: Yellow/низкоконтрастные фазные бейджи на проекторе
§5.1 правила; контраст-проверка — часть задачи DESIGN-TOKENS.md; литмус «с 4 м» (§5.3).

import json, math, random

class Value:
    def __init__(self, data, parents=(), op=""):
        self.data, self.grad, self.op = data, 0.0, op
        self._parents, self._backward = parents, lambda: None

def vadd(a, b):  # пример op; аналогично vmul/matvec-строки/tanh/sigmoid/bce
    out = Value(a.data + b.data, (a, b), "+")
    def _bw():
        a.grad += out.grad; b.grad += out.grad
    out._backward = _bw
    return out

def vtanh(a):
    out = Value(math.tanh(a.data), (a,), "tanh")
    def _bw():
        a.grad += out.grad * (1.0 - out.data ** 2)
    out._backward = _bw
    return out

def backward(root):  # topo + reverse (micrograd-канон)
    topo, visited = [], set()
    def build(v):
        if v not in visited:
            visited.add(v); [build(p) for p in v._parents]; topo.append(v)
    build(root)
    root.grad = 1.0
    for v in reversed(topo): v._backward()

### URL-state модуль (TS, ~30 LOC)

// src/player/urlState.ts
export function parseHash(hash: string): { step: number; lecture: boolean } {
  const p = new URLSearchParams(hash.replace(/^#/, ""));
  const step = Number.parseInt(p.get("step") ?? "0", 10);
  return {
    step: Number.isFinite(step) && step >= 0 ? step : 0,   // clamp сверху по trace.length
    lecture: p.get("mode") === "lecture",
  };
}
export function toHash(step: number, lecture: boolean): string {
  return `#step=${step}${lecture ? "&mode=lecture" : ""}`;
}
