# R3. Бесконечные эпохи и пошаговый движок: пересмотр центральной архитектурной развилки

**Фаза:** 01 (валидация H2/H3, кликабельный прототип) · **Дата:** 2026-11-03 · **Статус:** предложено, ждёт решения пользователя
**Входное направление пользователя:**

> «Как и в обучении, не должно быть ограничения на количество шагов (эпох), но при этом должна быть возможность пошагового исполнения каждой операции (как и сейчас) в эпохе, при завершении эпохи отображать и переходить в следующую, так же должна быть возможность прохода сразу к следующей эпохе (запустить сразу все шаги)»

**Реагирует на:** `.planning/research/ARCHITECTURE.md` (решение №1 «Deterministic replay over live stepping», Anti-Pattern 1), `PITFALLS.md` (№2 детерминизм, №9/10 persist, №11 память/рендер), `REQUIREMENTS.md` (DOCS-01/03/05, NFR-01/02), текущий код `src/player/store.ts` + `src/data/xor-trace.json` (14 шагов одного сэмпла, seed 43).

## 0. TL;DR

1. Направление меняет центральный инвариант: **трейс как статический артефакт умирает** («вычислить весь прогон при загрузке» невозможно для бесконечного прогона), но **детерминизм не умирает — он переезжает с артефакта на функцию**: `state = f(scenario, seed, epoch, step)`, одна чистая `advance()` для всех путей (шаг, fast-forward, назад, reload).
2. Рекомендуемый вариант — **(d): seeded live-движок + чекпойнты весов на границах эпох + оп-лог только текущей эпохи** (частный случай (b) с окном «одна эпоха»). Внутри эпохи UX в точности как сейчас (O(1) назад из лога), «бесконечность» = чекпойнт + реплей, fast-forward = батч того же `advance()`.
3. DOCS-05 сохраняется формулировкой, но меняется механизм: reload = детерминированный реплей до `(epoch, step)` (XOR — мгновенно даже на 1000-й эпохе; MNIST — кэш чекпойнтов в IndexedDB как ускорение, не источник истины). Кросс-браузерный hash-тест из «желательного» становится **обязательным** — трансценденталы теперь исполняются в рантайме браузера, а не только офлайн в Python.
4. NFR-02 переформулируется: фикстуры **первых K эпох** (пооперационно, ≤1e-6) + исполняемые **инварианты детерминизма** (повторный прогон байт-идентичен; путь не влияет на состояние; пошагово == fast-forward) + gradcheck. «100% операций» = 100% типов оп во всех режимах префикса + инварианты на хвост.
5. DOCS-01: **M = число шагов в эпохе** (XOR ≈ 56 при 4 сэмплах), индикатор двухуровневый («эпоха 2 · пример 3/4 · шаг 9/14»), добавляются AC на экран завершения эпохи и fast-forward; «завершение сценария» переопределяется как целевое условие (сходимость), не «последний шаг».
6. Для фазы 01 движок не нужен: мок-генератор достраивается до 3 эпох офлайн, стор переводится на координаты `(epoch, stepInEpoch)` — новый UX проверяется в H3-тесте без единой строки live-движка.

## 1. Разложение требования

| # | Под-требование | Следствие для архитектуры |
|---|----------------|---------------------------|
| R1 | Нет ограничения на число эпох (обучение «как в жизни») | Прогон **бесконечен** → никакой полный трейс не может существовать ни как контент, ни в памяти |
| R2 | Пошаговое исполнение каждой операции внутри эпохи (как сейчас) | Оп-гранулярность и данные шага (inputs/outputs/grads/provenance) сохраняются |
| R3 | Экран завершения эпохи + переход в следующую | Граница эпохи = первоклассный UI-объект; естественная точка чекпойнта |
| R4 | Fast-forward: запустить все шаги эпохи сразу | Пакетное исполнение без пошагового рендера + итоговый экран |

**Словарь.** Эпоха = полный проход по датасету. XOR: 4 сэмпла × ~13 оп-шагов (forward 6 + loss 1 + backward 5 + update 1) + мини-сводки ≈ **56 шагов на эпоху** + 1 экран эпохи. Текущий прототип показывает ровно 1/56 одной эпохи (один сэмпл).

**Ключевое следствие.** Решение №1 из ARCHITECTURE.md («выполнить весь прогон один раз при загрузке → неизменяемый RunTrace») опиралось на конечность прогона (`"epochs": 4` в формате сценария). R1 делает его неприменимым буквально, но **не отменяет его дух**: чистый плеер над данными шага, детерминизм by construction, UI никогда не кормит значения обратно в движок. Меняется носитель: вместо «весь трейс сразу» — «окно + чекпойнты + детерминированная достройка».

## 2. Новый центральный инвариант (замена «предвычисленный трейс»)

```
state(scenario, seed, epoch, step) — чистая детерминированная функция
advance(state, n)                  — единственная функция исполнения,
                                     используемая ВСЕМИ путями:
                                     пошаговый «Шаг», fast-forward, «назад»,
                                     reload-restore, переход к следующей эпохе
```

Следствия:

- **Шаг назад и reload корректны по построению**, если любой путь к `(epoch, step)` — это та же `advance()`. Чекпойнты — не «другой способ считать», а **кэш промежуточных состояний** `advance`.
- Требуется полная детерминированность движка в рантайме: seeded init + зеркальный PRNG (mulberry32 в TS и Python), **собственные `tanh`/`exp`** (ARCHITECTURE Pattern 2), фиксированный порядок суммирования. Сейчас числа рождает Python офлайн; в live-движке их рождает браузер → кросс-браузерный CI (Chromium/Firefox/WebKit) с сравнением hash-цепочки состояний становится обязательным, а не желательным (PITFALLS №2).
- `traceHash` из ARCHITECTURE трансформируется в **hash-цепочку**: `epochLogHash[e]` (хэш оп-лога эпохи) и `weightsHash[e]` (хэш весов на границе) — именно они сравниваются в тестах инвариантов (§7).

Что НЕ меняется: однонаправленный поток `scenario → engine → (окно трейса + чекпойнты) → player → UI`; UI остаётся чистым рендером; persistence только наблюдает.

## 3. Общие механики (не зависят от выбора варианта)

### 3.1 Координата позиции

`PlayerState.stepIndex` → `(epoch, stepInEpoch)` (+ производный `sample` внутри эпохи). Все клампы, `selectIsLast`, URL-роутер и e2e переводятся на эту координату. «Последний шаг» = последняя операция эпохи, а не прогона.

### 3.2 Чекпойнты на границах эпох

Снапшот весов (13 float64 для XOR) на каждой завершённой границе эпох. Политика удержания:

- **всегда:** epoch 0 (инициализация из сценария — она и так данные) + последние C≈5 эпох;
- **лестница:** эпохи 1, 2, 4, 8, 16, … — ограничивает глубину холодного реплея;
- **персистентность:** IndexedDB — **кэш** (проверяется `weightsHash`), не источник истины; на чужой машине/инкогнито — холодный реплей, детерминированно тот же результат.

Память: XOR — 13×8Б = ~100 Б/чекпойнт (сотни эпох — килобайты, несущественно). MNIST-масштаб (784-128-64-10, ~110k параметров ≈ 0.9 МБ/чекпойнт): лестница ~20 чекпойнтов ≈ 18 МБ в IDB, последние C в RAM ≈ 4.5 МБ — приемлемо; «хранить все чекпойнты всех эпох» (50 эпох = 44 МБ) — запрещено политикой.

### 3.3 Fast-forward

- XOR/спираль: `advance(state, остаток эпохи)` синхронно (<10 мс) → сразу экран завершения эпохи. NFR-01 не затрагивается (он про видимый шаг; FF — отдельный бюджет).
- MNIST-масштаб: тот же `advance` в **Web Worker** (шов уже предусмотрен `platform/worker.ts` в ARCHITECTURE) либо чанками по rAF с прогрессом; никогда не блокировать main thread > 100 мс. Worker ≠ риск детерминизма: тот же JS-движок, те же f64.
- Анимация «прогона» (опционально): лёгкий превью-тик каждые ~16 мс **из уже записанного лога** — без повторных вычислений; возможна только в вариантах с логом (b/c/d).

### 3.4 URL и persistence

- URL (источник истины позиции): `#/scn/xor?epoch=5&step=8&mode=…` (+ `seed`, только если отличается от сценарного дефолта). **Чекпойнты в URL не кладутся** — они рекомпьютабельны; кладётся только адрес в пространстве `(seed, epoch, step)`.
- Reload: parse URL → `advance` от epoch 0 или ближайшего валидного чекпойнта (IDB) → тот же экран. Глубокая холодная позиция — реплей с прогресс-индикатором (XOR: 1000 эпох ≈ единицы мс; MNIST: ограничен лестницей, см. §4 риски).
- localStorage — прежняя роль (прогресс-кэш, honest reset по версии схемы — PITFALLS №10). Смена версии движка может менять числа → та же политика честного сброса + баннер.
- Аналитика: + coarse-события `epoch_completed(loss)`, `epoch_fast_forwarded` — в существующую схему, без пошагового шума.

### 3.5 Порядок сэмплов

Фиксированный порядок `[0,1,2,3]` в v1 (минимальная детерминированность, соответствует текущему моку). Seeded-shuffle per epoch — только если контент попросит, тогда перестановка выводится из сценарного seed тем же зеркальным PRNG.

## 4. Варианты

### (a) Полностью live-движок, без лога шагов

Состояние модели в памяти; «Шаг» = исполнить следующую оп; назад = реплей от границы эпохи (или от seed). Детерминизм — seeded init + детерминированный порядок.

- **Шаг назад:** restore чекпойнта начала эпохи + `advance` до `step−1`. XOR: ~56 элементарных оп ≈ микросекунды, незаметно; «назад» на N шагов = один реплей (не N). На тяжёлых сценариях (макро-шаг MNIST) — на грани бюджета 100 мс при частых нажатиях. Данные шага для UI (inputs/outputs/grads/provenance) пересчитываются при каждом восстановлении — дёшево, но drill-down в «прошлое» без реплея невозможен.
- **Reload:** seed+epoch+step в URL; восстановление реплеем (XOR — мгновенно на любых глубинах; MNIST — холодный реплей до чекпойнта лестницы, ~секунды-десятки секунд без IDB-кэша).
- **Fast-forward:** `advance` батчем; анимации нет (нет лога) — только итоговый экран.
- **Память:** O(веса + текущая оп) — минимальная из всех.
- **NFR-02:** фикс-префикс первых K эпох пооперационно; хвост верифицируется инвариантами D1/D2 по `weightsHash` (§7).
- **Риск DOCS-05:** средний. Детерминизм конструируется, но «назад→вперёд→те же числа» и reload держатся только на дисциплине единой `advance`; любая рантайм-недетерминированность (Math.tanh и пр.) мгновенно ломает UX. Это буквально Anti-Pattern 1 из ARCHITECTURE — его можно реализовать корректно, но ценой постоянной бдительности.
- **Дельта от кода:** наибольшая. Плеер теряет trace-абстракцию (`trace.steps[i]`), drill-down/provenance — пересчёт на лету; переписывание всего, что уже написано и протестировано.

### (b) Live compute + материализация по требованию (ring buffer + чекпойнты)

Движок живой; каждый исполненный шаг логируется в ограниченное окно (последние W шагов, W ~ 1–2 эпохи); чекпойнты на границах эпох.

- **Шаг назад:** в пределах окна — O(1) чтение из лога (в точности текущий UX, `selectStep` без изменений); за окном — чекпойнт + реплей с перестройкой окна.
- **Reload:** как в (a); после restore окно перестраивается реплеем хвоста эпохи.
- **Fast-forward:** `advance` + запись лога эпохи; анимация из лога бесплатно.
- **Память:** O(W × размер шага + чекпойнты). XOR: лог эпохи ≈ 100–120 КБ; MNIST: окно макро-шагов + drill-сэмпл — мало. Единственный вариант, где W — настраиваемый параметр (гибкость = источник ошибок, если W настроен неверно).
- **NFR-02:** фикс-префикс + D1/D2/D3 + hash-цепочка лога как побочный проверяемый артефакт.
- **Риск DOCS-05:** низкий-средний: детерминизм + лог даёт материальное свидетельство (хэш окна).
- **Дельта от кода:** средняя — trace-абстракция сохраняется как «окно»; плеер почти не меняется.

### (c) Ленивая генерация трейса эпохами (расширение текущего)

Трейс достраивается ровно на эпоху вперёд по требованию; «бесконечность» = append. Без вытеснения память растёт линейно: текущий JSON ≈ 2 КБ/шаг × 56 шагов ≈ **110 КБ/эпоху → 100 эпох ≈ 11 МБ, 1000 эпох ≈ 110 МБ** — вытеснение нужно уже на XOR при долгой лекции. С вытеснением «назад в вытесненную эпоху» = регенерация = чекпойнт + реплей, т.е. (c) вырождается в (b).

- **Шаг назад:** O(1) по всему посещённому (до вытеснения) — лучший UX на малых глубинах.
- **Reload:** тот же адрес в URL; регенерация посещённых эпох.
- **Fast-forward:** генерация шагов без рендера (та же запись в память!).
- **Память:** растёт ∝ числу посещённых эпох до вытеснения — единственный вариант с неограниченным по конструкции ростом.
- **NFR-02:** удобно для инкрементального хэша достроенных эпох; остальное как (b).
- **Риск DOCS-05:** низкий до вытеснения; после — требования к реплею как в (b).
- **Дельта от кода:** минимальная (кламп/длина становятся динамическими) — и это его **единственное** реальное преимущество; при серьёзном применении он не выдерживает масштаба.

### (d) Seeded live + per-epoch чекпойнты + лог только текущей эпохи

= (b) с жёстким окном «ровно текущая эпоха (+ опционально хвост предыдущей)». Лог прошлых эпох отбрасывается; шаг назад в прошлую эпоху = restore её чекпойнта + реплей до конца (XOR — микросекунды).

- Все свойства (b); память наиболее предсказуема: O(1 эпоха лога + лестница чекпойнтов).
- Единица верификации NFR-02 = эпоха: лог текущей + `weightsHash` границы — чистая формулировка инвариантов.
- Окно «эпоха» совпадает с UI-объектом (экран завершения эпохи) — нет отдельного параметра W, меньше режимов, меньше ошибок.

## 6. Рекомендация

**(d).** Обоснование по критериям:

1. **UX «назад» внутри эпохи неотличим от текущего** (O(1) из лога) — самый частый жест пользователя не деградирует; (a) держит его только ценой реплея, что на тяжёлых сценариях рискует бюджетом 100 мс.
2. **Память ограничена по построению**, без параметра W: одна эпоха лога + лестница чекпойнтов; MNIST-масштаб закрыт IDB-кэшем (§3.2). (c) с вытеснением — это и есть (d), но с лишним промежуточным состоянием.
3. **Кодовая непрерывность**: trace-абстракция, drill-down, provenance, `selectStep` — всё выживает как «окно текущей эпохи»; переписывается только координата позиции и границы клампов. (a) потребовал бы переписать написанное и протестированное.
4. **Совпадение единиц**: окно = эпоха = экран завершения = чекпойнт = единица NFR-02-верификации. Одна абстракция на все слои — меньше режимов, меньше ошибок.
5. **DOCS-05 риск минимален среди live-вариантов**: детерминизм и его свидетельства (hash-цепочка) материальны; все пути — одна `advance`.

Отвергнутое и почему: (a) — Anti-Pattern 1 из ARCHITECTURE остаётся верным предупреждением; его можно делать аккуратно, но нет выигрыша, компенсирующего потерю O(1)-назад и трейс-абстракции. (c) — не выдерживает R1 по памяти, вырождается в (b)/(d). (b) — допустим, но его гибкость (W как параметр) не нужна: естественная граница окна уже задана требованием R3.

**Контр-аргумент (честно):** на XOR разницы между (a) и (d) пользователь не заметит никогда; (a) — меньше кода. Выбор (d) — это страховка на спираль/MNIST и сохранение уже написанного плеера, оплаченная ~100–150 строками управления логом/чекпойнтами.

## 7. NFR-02: реформулировка под бесконечный поток

Буквальное «100% операций каждого сценария против эталона» невыполнимо для бесконечного прогона. Замена:

1. **Фикс-префикс (пооперационный эталон).** Первые K=3 эпохи каждого сценария: каждый оп каждого сэмпла каждой эпохи сравнивается с PyTorch float64 / micrograd (те же веса, seed, порядок) при rtol ≤ 1e-6 + atol. K=3 покрывает разные числовые режимы (инициализация, ранние/поздние обновления). Фикстуры коммитятся; регенерация байт-стабильна (`make fixtures && git diff --exit-code`) — как в текущем плане.
2. **Инвариант D1 (повторяемость).** Два независимых прогона движка от одного seed до эпохи N (сценарно-масштабной, напр. 25–100) дают байт-идентичные цепочки `weightsHash[e]` и `epochLogHash[e]`. Кросс-браузерно в CI (Chromium/Firefox/WebKit) — обязательный тест, см. §2.
3. **Инвариант D2 (независимость от пути).** `state(e,s)`, достигнутое (i) пошагово, (ii) fast-forward'ом, (iii) restore с чекпойнта + реплей, — байт-идентично. Property-тест на случайных `(e,s)`.
4. **Инвариант D3 (консистентность чекпойнтов).** Стриминговое состояние на границе эпохи == состояние, восстановленное из чекпойнта этой эпохи.
5. **Gradcheck (без изменений).** Конечно-разностная проверка каждого типа оп — не зависит от фикстур и остаётся первою линией обороны.

Переформулировка покрытия: «100% **типов операций** во всех числовых режимах фикс-префикса + инварианты D1–D3, распространяющие корректность на неограниченный хвост». Хвост не «проверен против эталона», а «наследует корректность детерминированной функции, проверенной на префиксе и инвариантах» — это максимум достижимого для бесконечного потока и должно быть зафиксировано явно.

## 8. Изменения в REQUIREMENTS.md

### DOCS-01 (пошаговое исполнение)

- **«шаг N из M»: M = шагов в эпохе** (XOR ≈ 56), не всего прогона. Рекомендуемый индикатор — двухуровневый: «эпоха 2 · пример 3 из 4 · шаг 9 из 14» + фазовая полоса (forward ▸ loss ▸ backward ▸ update); плоский «шаг 37 из 56» не рекомендован (PITFALLS, UX-таблица: плоский счётчик теряет ориентацию).
- **Новый happy path (R4):** Given пользователь в середине эпохи, When нажимает «Запустить эпоху целиком», Then все оставшиеся операции исполняются без пошагового рендера (< 1 с на XOR/спираль; прогресс/worker на MNIST) и отображается экран завершения эпохи.
- **Новый happy path (R3):** экран завершения эпохи показывает loss до/после, динамику по эпохам (sparkline), для XOR — счётчик верных примеров; кнопки «Следующая эпоха по шагам» / «Запустить следующую сразу».
- **Edge case (переписать):** «последний шаг backward → завершение walkthrough» → «последняя операция эпохи → корректный экран завершения эпохи (не пусто/NaN)». Завершение **сценария** = достижение сценарного целевого условия (например, XOR: все 4 примера классифицированы верно / loss < порога) → итоговая сводка + предложение следующего сценария (DOCS-03), **после чего обучение можно продолжать** (нет лимита).

### DOCS-03 (прогрессия)

- «XOR отмечен завершённым» — условие маркировки при бесконечности: достижение целевого условия (или явное «Завершить сценарий» после ≥ 1 эпохи). Предложение следующего сценария появляется на экране эпохи после достижения цели — мягко, не гейтит.

### DOCS-05 (лекционный режим)

- Внешняя формулировка не меняется («перезагрузка по той же ссылке возвращает то же состояние маршрута»). Implementation-гарантия: состояние ≡ `f(seed, epoch, step)`, рекомпьютабельно; IDB-чекпойнты — ускоряющий кэш (проверяется хэшем), не источник истины; инкогнито/чужая машина — холодный реплей с тем же результатом (плейсхолдер-тест из PITFALLS №9 расширяется: «открыть ссылку с `epoch=7` на другой машине»). Смена версии движка = honest reset (PITFALLS №10).

### NFR-01

- Шаг пользователя — по-прежнему < 100 мс. Явно вывести из-под бюджета: fast-forward эпохи (бюджет < 1 с XOR/спираль, async на MNIST) и reload-restore (прогресс-индикатор, ограничен лестницей чекпойнтов).

### NFR-02

- Текст «100% операций каждого сценария…» → формулировка из §7 (фикс-префикс K эпох + D1–D3 + gradcheck). Без этой правки требование становится формально невыполнимым.

## 9. Стейджинг для фазы 01 (прототип без движка)

H3-тест должен проверить новый UX **до** строительства live-движка (движок — Phase 2 по CONTEXT фазы 01):

1. **`gen_mock_trace.py`**: генерировать E=3 эпохи (4 сэмпла каждая, SGD за каждый сэмпл) с маркерами `epoch`/`sample` в шагах и per-epoch сводками. Мок остаётся статическим JSON, рождённым Python'ом — детерминизм офлайн, ноль движка. Санити-фильтр распространить на «loss монотонно убывает по эпохам в среднем».
2. **`store.ts`**: координата `(epoch, stepInEpoch)` вместо глобального `stepIndex`; клампы по границам эпохи; `selectPosition` → двухуровневый индикатор. Это точка невозврата, которую лучше пройти на моке.
3. **UI**: экран завершения эпохи (R3) + кнопка «Запустить эпоху целиком» как мгновенный переход по мок-трейсу (R4, симуляция FF).
4. **H3-протокол**: задание «дойти до конца» переформулировать как «дойти до конца эпохи 2»; добавить наблюдение: понимает ли респондент переход эпох и индикатор.

Риск этого стейджинга: фиксация формата мока под эпохи, который потом выбрасывается при переходе на движок, — цена мала (генератор одноразовый), выгода — валидация центрального UX-изменения на реальных респондентах.
