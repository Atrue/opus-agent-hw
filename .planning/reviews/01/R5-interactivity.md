## 0. Резюме

**Рекомендуемая связка: Floating UI (@floating-ui/react) для тултипов + нативные CSS transitions/keyframes для подсветки и потока + точечный WAAPI для one-shot-эффектов. Анимационные фреймворки (Framer Motion, GSAP, react-spring, d3-transition, SMIL) — НЕ нужны.** Ключевая дидактическая находка: «бегущий пунктир» на активных рёбрах с направлением по фазе шага (forward → слева-направо, backward → справа-налево) — это ровно та визуализация, которая показывает «КУДА течёт градиент», и она делается чистым CSS (`stroke-dashoffset` keyframes) на существующем hand-rolled SVG без единой зависимости. Тултип — это лёгкий tier drill-down на тех же данных (`resolveRef` уже существует в NumberDrilldown.tsx:54), его тяжёлый контент (формула + подстановка + grad) и a11y-требования (UX-04) делают нативный `title`/CSS-псевдоэлемент несостоятельными; спор Floating UI vs собственный компонент решаем в пользу Floating UI (~10–15 KB gz) из-за collision-handling и эталонной a11y-семантики.

## 1. Пересмотр A-8: что именно меняется

A-8 («анимации смены шага — нет, мгновенная смена») принималась ради детерминизма (DOCS-05), проектора и NFR-01. Направление пользователя не отменяет эти ценности — оно уточняет separation of concerns:

- **Мгновенность сохраняется на уровне состояния и контента:** смена шага = мгновенный рендер финальных чисел/формул/подсветок (NFR-01 <100 мс, replay-детерминизм, лектор может «спамить» шаг без очереди эффектов). A-8 реформулируется: «смена шага мгновенна; анимация — опциональный презентационный слой ПОСЛЕ апдейта, никогда его не гейтит».
- **Анимация = чистая презентация поверх нового состояния.** Паттерн: React рендерит финальное состояние → CSS transition/keyframe доводит визуальное акцентирование (тинт, обводка, пунктир) от старого к новому. Стор (`store.ts` transition) остаётся анимационно-агностичным — в `PlayerState` не появляется ни одного анимационного поля.
- **FLIP не нужен:** Interaction Contract фиксирует слоты («смена шага не меняет высоты зон»); ни один элемент не перемещается между шагами — анимируются только подсветка/прозрачность/штрих. Layout-анимации — вне скоупа by design.

Это переформулировку фиксируем в 01-UI-SPEC как A-8-rev (см. §7).

## 2. Подпроблема 1 — тултипы/ховеры

Требование: ховер на число/звено → значение + вычисление (формула с подстановкой) + градиент/обратное значение. Это **почти mini-drilldown** — 3–5 строк тяжёлого контента, mono-шрифт, ширина ~260–360px. В FEATURES.md это TS-11 («tooltips are the lightest drill-down tier; same metadata powers full drill-down panels», planned P2 v1.x) — данные уже есть: `resolveRef(step, ref)` возвращает `{sym, value, provenance}`, формула шага и `step.grads` лежат в TraceStep. Тултип = тонкая обёртка над существующим резолвером, дублирования данных нет.

Критерии: (к1) тяжесть контента; (к2) a11y — фокус/клавиатура (UX-04: focus + ARIA; числа и рёбра уже `role="button" tabIndex={0}` — фокус-триггер бесплатен); (к3) мобильный тап (прототип десктоп ≥1024px по A-6, мобильный тир — Phase 3; соглашение: tap → сразу drill, тултип — hover/focus-only, drill — супермножество тултипа); (к4) размер зависимости; (к5) совместимость с hand-rolled SVG (якоря — SVG-элементы); (к6) лекционный режим (контент масштабируется через те же CSS-переменные `--num-size`).

### 2a. Нативный `<title>` + CSS-тултип — НЕ ГОДИТСЯ

- `<title>` в SVG: не стилизуется, задержка браузера ~1–2 с, многострочный тяжёлый контент (формула+grad) невозможен, поведение на фокусе нестабильно между браузерами. Для «мини-панели» несостоятелен.
- CSS-псевдоэлемент (`::after`): на SVG-элементах псевдоэлементы не поддерживаются браузерами; в HTML-части (StepPanel) — нет collision-handling (числа у правого края экрана → тултип выйдет за вьюпорт), нет hover-intent задержки, нет `aria-describedby`-механики. Экономия ~0 KB, но long-tail багов.
- Вердикт: только как деградация для `<title>`-заглушек, не как решение.

### 2b. Собственный React-тултип — жизнеспособен, но это long-tail

Плюсы: 0 зависимостей; layout приложения фиксирован (один экран, слоты стабильны) → размещение детерминировано per-region (диаграмма — сверху/снизу от якоря, StepPanel — влево), ~100–150 LOC + portal.
Минусы: вручную реализуются hover-intent delay, show/hide на focus/blur, Esc-dismiss, `id`/`aria-describedby`-менеджмент, clipping у краёв вьюпорта (а числа StepPanel стоят ровно у правого края — это не теоретический кейс), отмена по rapid re-hover. Это классические 20% усилий на 80% краевых случаев; баги здесь бьют по UX-04 в фазе, где a11y — явное требование.
Вердикт: приемлемый минималистский путь при жёстком бандл-пуризме, но не рекомендуется.

### 2c. Floating UI (@floating-ui/react) — РЕКОМЕНДУЕТСЯ

- ~10–15 KB gz (react-пакет + @floating-ui/react-dom), MIT, headless (никакого UI-контента навязывает — верстаем на своих токенах).
- Преемник Popper v2 (преемственность команды, 2022); именно его внутрях используют Radix/Base UI для позиционирования — это индустриальный стандарт без мажор-лока: API маленький (`useFloating` + `useInteractions`: `useHover`, `useFocus`, `useDismiss`, `useRole`).
- Из коробки: flip/shift (collision у правого края StepPanel закрыт), hover-intent delay, тултип-семантика через `useRole('tooltip')` (aria-describedby), dismiss по Esc. Якоря — DOM-элементы, включая SVG (getBoundingClientRect работает; на крайний случай — virtual elements).
- Контент — произвольный JSX → переиспользуем `SubscriptText`/`formatKey`/`resolveRef`; лекционный режим наследует `--num-size` автоматически, т.к. стилиуем токенами.
- Проверка совместимости: @floating-ui/react совместим с React 19 (использует стандартные хуки; команда поддерживает актуальные мажоры React).

### 2d. Base UI tooltip — легитимно, но преждевременно

- STACK.md зафиксировал триггер: «Base UI 1.x — отложен до Phase 2+, если появятся тултипы/модалки». Тултипы появились — триггер формально сработал, вариант обязан быть рассмотрен.
- Плюсы: полный a11y-паттерн из коробки; если в Phase 2+ появятся модалки/поповеры — одна система.
- Минусы: тянуть компонентную систему ради одного тултипа сейчас — инверсия зависимостей: мы выбираем дизайн-систему раньше, чем знаем её полный сценарий; tree-shaken-размер сопоставим с Floating UI (~15–25 KB gz, оценка MEDIUM — точную цифру снять при внедрении); API моложе (1.x), меньше накопленных примеров.
- Вердикт: пересмотреть когда появятся вторые примитивы (модалка/поповер); сейчас — Floating UI. Замена изолирована, если тултип-компонент обёрнут в один `NumberHint.tsx`.

## 3. Подпроблема 2 — подсветка звена и анимация потока

Текущее состояние: подсветка активной op уже state-driven (`activeGeometry` → класс `active` → casing/тинт, ArchitectureDiagram.tsx:58–111, 153–163) — смена мгновенная. Нужно: плавность подсветки + «поток» по рёбрам активного звена + пульс. Дидактическая цель: **видно, КУДА течёт вычисление/градиент на текущем шаге** — для backward это право→лево (ŷ → hidden → x), смена направления потока между фазами и есть ментальная модель backprop.

### 3a. Чистый SVG + CSS transitions/keyframes — РЕКОМЕНДУЕТСЯ (основа)

- **Плавность подсветки:** `transition: stroke .18s, fill .18s, opacity .18s, stroke-width .18s` на `.diag-node`/`.diag-edge`/`.diag-edge-casing`. Работает и для инлайн-стилей React (transition срабатывает на изменение computed value). Требуется микрорефакторинг: casing активного ребра сейчас монтируется условно (`{active && <line/>}`) — mount не анимируется transition'ом; рендерить постоянно с `opacity: 0 → 1` через класс.
- **Поток — «бегущий пунктир»:** на активных рёбрах слой `.diag-flow`: `stroke-dasharray: 8 6; animation: diag-flow 0.9s linear infinite; @keyframes diag-flow { to { stroke-dashoffset: -14; } }`. Отрицательный сдвиг двигает штрихи вдоль направления пути; рёбра нарисованы всегда `from → to` (x→h, h→ŷ), значит forward = отрицательный offset, backward = `animation-direction: reverse` (или `to { +14 }`). Направление выбирается CSS-селектором по data-атрибуту корня: `<svg data-flow="backward">` — один проп из `step.phase`, ноль JS-анимаций.
- **Пульс подсветки звена:** keyframes на opacity/stroke casing (например 2 такта при входе) — опционально, осторожно с проекторным мерцанием (Pitfall 6-дух: минимализм).
- prefers-reduced-motion: один `@media (prefers-reduced-motion: reduce) { animation: none; transition: none; }` гасит всё (§5).
- Печать/лекция: `@media print { .diag-flow { animation: none; } }` — статичный кадр; лекционный режим НЕ отключает поток (он дидактичен), только уважает reduced-motion.
- Стоимость: 0 зависимостей, ~40–60 строк CSS. 9 рёбер + 6 узлов — нагрузка ничтожна (Pitfall 11 неприменим: DOM-дерево не растёт, layout детерминирован и не пересчитывается).

### 3b. SMIL — ❌

`<animate>` игнорирует `prefers-reduced-motion` (нет стандартной интеграции), restart-механика конфликтует с React-перерендером (DOM-узел пересоздаётся → анимация молча перезапускается/теряется), императивное управление `beginElement()` неудобно для связки со стором. Chrome «раздепрекировал» SMIL, но экосистемного ренессанса нет. Ничего не даёт поверх CSS keyframes.

### 3c. WAAPI из React — РЕКОМЕНДУЕТСЯ точечно (для one-shot)

`element.animate()` в `useEffect` по ключу `stepIndex`: one-shot «волновой пробег» по рёбрам активного звена при входе в шаг (600 мс, затем steady-state от CSS), с `cancel()` в cleanup — rapid-stepping лектора обрабатывается корректно (предыдущая анимация отменяется, ничего не копится в очереди). Гейт одной строкой: `matchMedia('(prefers-reduced-motion: reduce)')`. Нужен только если CSS-continuous потока и transition-подсветки окажется недостаточно (сценарии: секвенирование forward-сигнал → затем backward-сигнал на matvec-grad шагах). Не добавлять превентивно (YAGNI, Pitfall 8-дух).

### 3d. d3-transition — ❌

Императивная мутация атрибутов DOM, которым владеет React — классическая проблема двойного ownership (d3 пишет stroke, React перерендер перетирает). STACK.md уже отверг полный d3 по этой же причине. Для 9 рёбер абсурдно.

### 3e. Framer Motion (motion) — ❌ (избыточен)

~30–45 KB gz. Сильная сторона — mount/unmount и layout/FLIP-анимации (`AnimatePresence`) — у нас отсутствуют by design (слоты стабильны, элементы персистентны, меняются классы). SVG-атрибутивная анимация (dashoffset) в нём не лучше CSS. Платим бандлом и второй моделью анимации ради ничего.

### 3f. GSAP — ❌

Лучший timeline-инструмент, но: ~25–30 KB gz core, императивный (рефы + useGSAP — тот же dual-ownership, хоть и дисциплинируемый), лицензия custom («no-charge», после Webflow все плагины бесплатны с 3.13 — но не OSI). Наш сценарий (2 направления потока, пульс, transition подсветки) не требует timeline-мощности. Дидактической ценности сверх CSS не добавляет.

### 3g. react-spring — ❌

Физические пружины уместны для интерактивного драг/жестов; у нас нет ни драга, ни жестов. ~15–20 KB gz + async-модель рендера ради linear/ease кривых — не о чём.

### 3h. Canvas/WebGL слой частиц — отложить (R3/MNIST-путь)

На MNIST пер-рёберная анимация невозможна (Pitfall 11: 784 входа), но STACK уже решил агрегацию («784 входа — один узел-вентилятор») → диаграмма остаётся ~6 узлов / ~5 агрегированных рёбер и CSS-поток масштабируется без изменений. Canvas-слой массовых частиц (плотность потока ∝ |grad|) — осознанная опция будущего fast-forward эпох (R3) и heat-карт (уже запланирован Canvas 2D для пиксельных хитмапов) — если агрегированного пунктира окажется дидактически мало. Решение о частицах принимать по материалу R3-прототипа, не сейчас.

## 4. Подпроблема 3 — архитектура связки «мгновенный state + анимация»

### 4.1 Принцип: финальное состояние сразу, декорация сверху

1. Смена шага: `transition()` стора → React рендерит **финальный** слайд мгновенно (числа, формулы, `activeGeometry`-подсветки уже на месте) — NFR-01 и DOCS-05-детерминизм не затронуты: числа НИКОГДА не появляются через анимацию.
2. Анимационный слой читает только `(stepIndex, phase, active)` — уже вычисляемые значения; реализуется: (а) CSS-классами (декларативно, persistence = рендер) и (б) опционально one-shot WAAPI в эффекте с отменой.
3. Идемпотентность при rapid-stepping: CSS transition автаргетится к новой цели; WAAPI-one-shot отменяется в cleanup; бесконечный пунктир — просто класс, не копится. Стор не знает об анимациях → replay/URL-hash/печать не меняются.

### 4.2 prefers-reduced-motion и лекционный режим

- Один глобальный блок в index.css гасит `animation`/`transition` — обязательный guard-тест (vitest или e2e-assert на вычисленный стиль), чтобы_media-queries не «протухли» при рефакторинге.
- Лекционный режим (`.lecture`) анимации НЕ выключает: поток — дидактический контент, а не украшение; проекторная стабильность обеспечивается тем, что анимируются только цвет/штрих/прозрачность (никакого layout/paint-шифта слотов). Пульс делаем деликатным или исключаем вовсе (мерцание на проекторе — Pitfall 6-дух).
- Печать: `@media print` останавливает пунктир (статичный кадр).

### 4.3 e2e: детерминизм 28 скриншотов

Сейчас скриншоты пишутся как self-check-материал (без pixel-diff), но зависимость всё равно есть (будущий pixel-diff, стабильность материала для юзабилити). Решение — **единственный рычаг: Playwright `page.emulateMedia({ reducedMotion: 'reduce' })`** в beforeEach e2e:

- гасит ВСЕ CSS-анимации/переходы → скриншоты ловят финальный кадр, флаков ноль;
- одновременно это живая проверка того, что reduced-motion-путь реально работает (a11y-тест бесплатно);
- дублировать app-флагом (`#still=1`) не нужно — один механизм, одна правда. WAAPI-эффекты, если появятся, гейтятся тем же matchMedia → тоже выключены.

### 4.4 Путь к R3 (fast-forward эпох) и MNIST

- Fast-forward = интервальное `jumpTo` + непрерывный CSS-поток на агрегированных рёбрах — масштабируется без изменений; one-shot WAAPI при быстрой промотке подавлять (порог длительности шага) — заложить в дизайн хука сразу.
- MNIST: агрегация входов (STACK) сохраняет малое число рёбер → CSS-поток переносится as-is; толщина/скорость потока ∝ |grad| слоя — дешёвая шкала силы градиента без частиц. Canvas-частицы — только если R3-материал покажет недостаточность.

### 4.5 Тултип × drill × анимация (единая модель прогрессивного оголения)

Tier-модель, согласованная с Pitfall 5 (анти-«стена цифр») и TS-11:

| Tier | Триггер | Контент | Реализация |
|---|---|---|---|
| 0. Видно на шаге | — | 3–7 ключевых чисел + подсветка | StepPanel + CSS-highlight (есть) |
| 1. Тултип | hover / Tab-фокус | значение + формула с подстановкой + grad (если есть) | Floating UI, `resolveRef` re-use |
| 2. Drill | клик / Enter | exact-repr + provenance + цепное правило | NumberDrilldown (есть) |

Тултип на фокусе закрывается Esc/blur (`useDismiss`), не перехватывает клик (hover ≠ click), на тач-устройствах tier 1 пропускается (tap → сразу drill) — A-6 это покрывает до Phase 3.

## 6. Рекомендация и план внедрения

**Связка: Floating UI (тултипы) + CSS transitions/keyframes (подсветка, пунктир-поток) + WAAPI (только если понадобится секвенирование one-shot). Фреймворки анимации — не нужны.**

1. **Шаг 1 (CSS-основа, 0 зависимостей):** переходы подсветки (casing persistent-render + opacity), `.diag-flow` пунктир с `data-flow`-направлением по фазе, глобальный `prefers-reduced-motion`-блок + `@media print`; рефакторинг `{active && <line/>}` → постоянный рендер с классом. e2e: добавить `emulateMedia({ reducedMotion: 'reduce' })`.
2. **Шаг 2 (тултипы):** `pnpm add @floating-ui/react`; компонент `NumberHint` (единая обёртка: якорь = value-btn/узел/ребро, контент из `resolveRef` + формула + grad-строка при наличии); обёртка изолирует замену на Base UI в Phase 2+, если появятся модалки.
3. **Шаг 3 (опционально, по юзабилити-материалу):** WAAPI one-shot «пробег сигнала» на matvec/matvec-grad шагах с cancel-on-cleanup и порогом подавления при быстрой промотке (задел под R3).
4. **Документация:** A-8-rev в 01-UI-SPEC (мгновенный state + презентационная анимация), обновить STACK.md (Floating UI в Supporting Libraries; Base UI-триггер переоценён — остаётся для модалок), 01-DESIGN-TOKENS.md — тайминги (transition ~180 мс, flow period ~0.9 с) как токены.

## 7. Риски и открытые вопросы

- **Точный gz-размер @floating-ui/react и Base UI tooltip** — снять при внедрении (`vite build` + report; оценки 10–15/15–25 KB — MEDIUM confidence).
- **Пульс на проекторе** — включать только после литмуса с 4–5 м; по умолчанию только плавная подсветка + пунктир.
- **Тултип на лекционном режиме** — ширина/перенос формулы при 32px: проверить на шаге с длинной формулой (матvec-grad); при необходимости кап ширины с переносом строки формулы.
- **Скорость пунктира как семантика** — не перегрузить: одна скорость для всех рёбер (дидактика — направление и принадлежность звену, а не «чья-то скорость»); вариативность (толщина ∝ |grad|) — отдельное решение Phase 2 после юзабилити.
- **Быстрая промотка (будущий R3):** подтвердить, что CSS-only непрерывный поток не создаёт perceived-jank при 2–4 шагах/с (скорее всего нет — анимация независима от частоты шагов).
