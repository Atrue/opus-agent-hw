## 0. Резюме (TL;DR)

Рекомендуется **вариант B (двухуровневый Tensor-first) как каркас + именование и паттерны из подмножества PyTorch (из C) + recorder-флаг из D**. ## 1. Вопрос и рамки

### 1.1 Что именно решаем

Фаза 1 построила кликабельный прототип поверх предвычисленного JSON-трейса (`src/data/xor-trace.json`, 14 шагов). Числа генерирует Python с micrograd-семантикой (`gen_mock_trace.py`: класс `Value` + функции `vadd/vmul/vtanh` + topo-`backward` + gradcheck). Фаза 2 должна заменить «числа из Python» на **собственный TS-движок**, и направление пользователя фиксирует его внутренний API: ООП-тензор с сигнатурами, похожими на Python, чтобы (а) код трейс-билдера читался как учебный PyTorch-цикл, (б) сниппеты в нарративе («в PyTorch это `torch.matmul(W, x)`) соответствовали реальному движку, (в) будущий R2-playground со студенческим кодом не потребовал переписывания движка.

Важно развести двух потребителей «похожести на Python»:

| Потребитель | Когда появляется | Что ему нужно |
|---|---|---|
| Автор трейс-билдера (мы) | Фаза 2 | читаемый API построения графа: `W1.matmul(x).add(b1).tanh()` |
| Студент (сниппеты в UI, живой код) | сниппеты — Фаза 2; редактор кода — R2 | имена и семантика 1:1 с `torch` |

В v1 студенческого редактора кода нет — это главный аргумент против полного PyTorch-словаря (§5, §9).

### 1.2 Ограничения, против которых меряем варианты

- **NFR-02:** все ops всех сценариев против micrograd/PyTorch float64, rel ≤ 1e-6, golden-фикстуры.
- **NFR-01:** шаг < 100 мс (при выбранной архитектуре «trace-on-load + pure player» — тривиально; реальный бюджет — **время построения трейса**: < 1 c XOR/спираль, < 3 c MNIST-подмножество).
- **DOCS-02:** drill-down до каждого числа: provenance = операция + родители + локальная производная (chain-rule развёртка в backward).
- **MNIST (Фаза 3):** 784-32-16-10 ≈ 25.8k весов, 1–2k сэмплов, макро-шаги по эпохам.
- **Совместимость:** UI уже потребляет `TraceStep` из `src/player/types.ts` (schemaVersion 1) — движок должен уметь эмитить ровно эту схему, чтобы Фаза 2 не переписывала UI.
- **Ноль зависимостей** в domain-слое (STACK.md: свой движок, никакого TF.js/WASM).

## 2. Общие развилки (до вариантов)

### 2.1 Operator overloading в TS невозможен — и это нормально

JS-движки не позволяют перехватить `+ - * /` между объектами: `Symbol.toPrimitive`/`valueOf` возвращают примитив и теряют граф. Proxy не помогает (арифметика не проходит через traps). Следствия:

- «Похожесть на Python» достижима только на уровне **имён методов и структуры цепочки**: `(x * w + b).tanh()` → `x.mul(w).add(b).tanh()`.
- Это сближает все варианты: в TS даже micrograd-порт неизбежно превращается в методы `add/mul/tanh` — ту же поверхность имён, что у PyTorch-тензорa. То есть направление пользователя на практике означает «методный словарь PyTorch на механике micrograd», а не «инфиксные операторы».
- Отвергнутые курьёзы: tagged-template DSL (`` g`${x} * ${w} + ${b}` `` умеет строить дерево выражений, но теряет типизацию по операторам, удивляет и всё равно не PyTorch); Unicode-методы (`x['+']`) — то же самое, но хуже.
- Функциональная форма (`add(a, b)`) полезна только для лоссов и симметричных случаев — в PyTorch они и живут в `torch.nn.functional`: `F.binary_cross_entropy(pred, y)`. Рекомендация: **методы для поэлементных/матричных ops, функциональное пространство `F` для лоссов** — ровно как в torch.

### 2.2 Мутация vs иммутабельность: модель Python воспроизводима и правильна

Python-семантика (micrograd и PyTorch совпадают):

- forward-op создаёт **новый** узел/тензор; `data` после создания не меняется;
- `grad` — **мутируемое накапливаемое** поле: `p.grad += ...` в `_backward`; повторный `backward()` без `zero_grad()` аккумулирует — это нагрузочная семантика, её надо сохранить;
- оптимизатор мутирует параметры на месте: micrograd `p.data += -lr * p.grad`, PyTorch `opt.step()`;
- `zero_grad()` — явный сброс.

Рекомендация: **повторить точно** — forward иммутабелен, `grad`/`step()` мутируют. Граница иммутабельности проходит не внутри движка, а на выходе: RunTrace замораживается при записи (числа копируются в шаги в момент записи — иначе поздний `opt.step()`, мутирующий `data` параметров, испортит историю). Это развязывает «живой мутирующий граф» (внутри прогона) и «неизменяемый трейс» (контракт UI и тестов) — противоречия между направлением пользователя и Architecture Decision №1 (deterministic replay) нет.

Чего не эмулируем (лишнее для v1): `retain_graph`, `detach()`, in-place ops (`add_`), `no_grad`, `Parameter` как отдельный тип.

### 2.3 Найденное противоречие research-доков: гранулярность ops

- ARCHITECTURE.md §1: гранулярность узла — **всегда операция** (matvec/add/tanh/loss), не скаляр.
- STACK.md Engine Architecture п.2: гранулярность — **часть сценария**: XOR/спираль — скалярные ops «как в micrograd», MNIST — fused ops.

Это два разных движка поведения. Рекомендация: **единообразный op-level** (по ARCHITECTURE.md): одна лента, один golden-конвейер, скалярный уровень — только ленивый drill-down-экспандер, а не альтернативный путь исполнения. Аргументы: скалярный путь для XOR даёт вторую поверхность golden-тестов и второй порядок суммирования, который надо сверять; op-level уже соответствует прототипу Фазы 1 (шаги matvec/add/tanh в xor-trace.json) и иерархии DOCS-02 (диаграмма → слой → операция → число). Против скалярного шагового режима есть и явный анти-паттерн 4 в ARCHITECTURE.md.

## 3. Вариант A — чистый micrograd-порт (скалярный Value)

### 3.1 Сигнатуры

TS (порт 1:1 из `gen_mock_trace.py`, методы вместо операторов):

```ts
class Value {
  data: number; grad: number; op: string; parents: Value[]
  private backwardFn: () => void
  constructor(data: number, parents: Value[] = [], op = '')
  add(o: Value): Value
  mul(o: Value): Value
  tanh(): Value; sigmoid(): Value; pow(n: number): Value
  backward(): void   // topo-сортировка + обратный проход, root.grad = 1
}

const L = x.mul(w1).add(b1).tanh().mul(w2).add(b2).sigmoid().bce(y)
L.backward()          // w1.grad накоплен
```

Python (micrograd):

```python
L = ((x * w1 + b1).tanh() * w2 + b2).sigmoid() ...
L.backward()          # w1.grad
```

Матрицы = вложенные `Value[][]`: как только появляются матрицы, «ООП-чистота» кончается — matvec это уже **функция** `matvec(w1v: Value[][], x: Value[]): Value[]`, а не метод класса. Класс существует только на скалярном уровне.

### 3.2 Оценка

| Критерий | Оценка |
|---|---|
| Соответствие micrograd | **Максимальное** — это и есть micrograd: тот же порядок создания узлов, тот же порядок суммирования → golden против `gen_mock_trace.py` сходится почти бит-в-бит |
| Соответствие PyTorch | **Низкое**: нет тензора, нет `matmul`, студент видит «скалярный суп», а не те операции, которые он потом напишет в torch. Цель направления пользователя не достигается |
| Drill-down (DOCS-02) | **Бесплатный и идеальный**: каждое число — сам `Value` с `data/grad/op/parents`. Локальная производная прячется в замыкании — для показа надо добавить поле `localGrad` (расширение micrograd) |
| NFR-01 / MNIST | **Провал по времени построения трейса**: ~26k весов → ~60–80k аллокаций `Value`+замыканий на один сэмпл; эпоха 2k сэмплов ≈ 1.2–1.6×10⁸ аллокаций ≈ 5–15 с только на GC/аллокации (вне бюджета < 3 c). XOR/спираль — без проблем (~50–300 Values на проход) |
| Объём кода | ~150–250 LOC движка |

### 3.3 Вердикт

**Не как единственный движок.** Но A не выбрасывается: (а) это готовый проверенный код для порта — `backward()` из `gen_mock_trace.py` переносится в TS построчно; (б) скалярный Value-уровень — естественный язык drill-down-экспандера внутри варианта B; (в) скалярные golden-фикстуры (gradcheck-числа генератора) остаются референсом второго уровня.

## 4. Вариант B — двухуровневый: Tensor (векторизованный) + скалярный drill-down

Текущий выбор ARCHITECTURE.md/STACK.md. Оценивающий разбор — по запросу задачи.

### 4.1 Сигнатуры

TS:

```ts
class Tensor {
  readonly data: Float64Array; readonly shape: number[]
  grad: Float64Array | null            // мутируется backward(), см. §2.2
  readonly requiresGrad: boolean
  readonly op: OpName                  // 'matmul' | 'add' | 'tanh' | ...
  readonly parents: readonly Tensor[]  // для topo/backward и provenance

  static of(values: number[]): Tensor
  matmul(o: Tensor): Tensor            // this · o; z1 = W1·x → W1.matmul(x)
  add(o: Tensor): Tensor
  tanh(): Tensor; sigmoid(): Tensor
  bce(target: Tensor): Tensor          // + F.bce(pred, y) — см. §8
  backward(): void                     // micrograd: topo + обратный проход
  zeroGrad(): void
}

// трейс-билдер читается как учебный PyTorch-цикл:
const z1 = W1.matmul(x).add(b1)        // формула шага: z1 = W1·x + b1
const a1 = z1.tanh()
const yhat = a1.matmul(W2).add(b2).sigmoid()
const L = yhat.bce(y)
L.backward()                            // во всехparents накапливаются .grad
opt.step()                              // W.data -= lr * W.grad (на месте)
opt.zeroGrad()
```

Python/PyTorch-эквивалент:

```python
z1 = torch.matmul(W1, x).add(b1)        # или z1 = W1 @ x + b1
a1 = z1.tanh()
yhat = a1.matmul(W2).add(b2).sigmoid()
L = F.binary_cross_entropy(yhat, y)
L.backward()
opt.step(); opt.zero_grad()
```

Расхождение со студентческим PyTorch — одно и честное: `nn.Linear` хранит W как (out×in) и делает `x @ W.T`. Мы храним W в ориентации формулы (`z = W·x`, строки = нейроны) и **не прячем транспонирование** — оно и в трейсе не нужно. Отображение фиксируется в сниппетах нарратива: `W1.matmul(x) ↔ torch.matmul(W1, x)`.

### 4.2 Соответствие семантике

- **Механика — micrograd:** граф узлов с `_backward`-замыканиями, topo-сортировка, аккумуляция `grad`, `backward()` от скаляра. Порт напрямую из `gen_mock_trace.py` (уже с gradcheck-подтверждением).
- **Поверхность ops — PyTorch:** `matmul/add/tanh/sigmoid/backward/zero_grad` — именно те операции, из которых состоит walkthrough; шаги трейса = ops = вызовы методов 1:1.
- Композиция «механика micrograd + словарь torch» покрывает направление пользователя без эмуляции инфраструктуры torch (§5).

### 4.3 Drill-down, golden, перф, объём

- **Drill-down (DOCS-02):** Tensor-op хранит операнды; скалярный экспандер раскрывает `z1[2]` лениво по тем же формулам и **в том же порядке суммирования**, что и векторное ядро (иначе числа разойдутся — см. риск Р-1). Для backward — цепочка «∂L/∂W1[j][i] = ∂L/∂z1[j] · x[i]» с переходами вверх по графу: это и есть вариант A, собранный на лету как view-слой.
- **Golden (NFR-02):** основной канал — op-level фикстуры из PyTorch float64. Порядок суммирования наш (наивные циклы) vs BLAS — расхождение ~1e-14, допуск 1e-6 с запасом ×10⁸; собственные `tanh/exp` (решение ARCHITECTURE.md) закрывают трансцендентные функции. Скалярные фикстуры генератора — второй, уточняющий канал.
- **Перф (NFR-01, MNIST):** ~5×10⁴ flops на проход — доли мс; эпоха 2k сэмплов — десятки мс; XOR — микросекунды. Бюджеты построения трейса выполняются на порядки.
- **Объём:** tensor.ts ~150, ops (fwd+bwd) ~150, graph/backward ~100, trace-билдер ~100–150, provenance-экспандер ~200–300. Итого ~700–850 LOC — подтверждает оценку ARCHITECTURE.md (500–800, без учёта provenance).

### 4.4 Критическая оценка выбора (что нашлось)

Выбор в целом **здоров** — это единственный вариант, одновременно закрывающий PyTorch-сигнатуры, DOCS-02 и MNIST-перф. Слабые места:

- **Р-1. Двойная реализация математики каждой op** (векторное ядро + скалярная формула drill-down). Заявление STACK.md «число в drill-down = число движка по построению» верно только при **идентичном порядке суммирования** — это инвариант, который надо сделать проверяемым: фикстуры расширить несколькими «просверленными» индексами (сравнение drill-down-числа с оп-выходом), не только оп-уровневыми значениями.
- **Р-2. Скрытая стоимость backward drill-down.** Локальные производные и chain-rule развёртка — фактически второй, скалярный движок (~200–300 LOC). В оценках STACK.md он не был посчитан; бюджетировать явно.
- **Р-3. Противоречие STACK.md ↔ ARCHITECTURE.md по гранулярности** (§2.3). Для направления «ООП-тензор» единый op-level строго проще: один класс, одна лента, один конвейер фикстур.
- **Р-4. Соблазн «ленивости везде».** Держать линию ARCHITECTURE.md: eager-прогон трейса при загрузке + ленивый только drill-down-view. Не делать ленивым построение трейса.

### 4.5 Вердикт

**База рекомендации.** Закрывает все ограничения; риски известны и купируемы тестами.

## 5. Вариант C — PyTorch-подобный API: Module/Sequential/F/SGD

### 5.1 Сигнатуры

TS:

```ts
abstract class Module {
  abstract forward(x: Tensor): Tensor
  parameters(): Tensor[]
  zeroGrad(): void
}
class Linear extends Module { /* W: Tensor, b: Tensor */ }
class Sequential extends Module { /* слои */ }
class SGD {
  constructor(params: Tensor[], lr: number)
  step(): void; zeroGrad(): void
}

const model = new Sequential(new Linear(2, 3), new Tanh(), new Linear(3, 1), new Sigmoid())
const opt = new SGD(model.parameters(), 0.5)
opt.zeroGrad(); F.bce(model.forward(x), y).backward(); opt.step()
```

Python/PyTorch:

```python
model = nn.Sequential(nn.Linear(2, 3), nn.Tanh(), nn.Linear(3, 1), nn.Sigmoid())
opt = torch.optim.SGD(model.parameters(), lr=0.5)
opt.zero_grad(); F.binary_cross_entropy(model(x), y).backward(); opt.step()
```

Максимальное сходство из всех вариантов — вплоть до цикла обучения.

### 5.2 Оценка

| Критерий | Оценка |
|---|---|
| Соответствие PyTorch | **Максимальное**: студент дословно переносит имена и цикл |
| Соответствие micrograd | Механика та же, что в B (не меняется) |
| Drill-down | **Не помогает**: Module/Sequential инкапсулируют последовательность ops — трейс-билдеру придётся инструментировать `forward` хуками, чтобы получить пошаговую ленту. Сценарий и так декларативный JSON — Module не добавляет ценности для walkthrough |
| Golden / перф | Те же, что в B (не меняются) |
| Объём | B + 400–700 LOC (Module/Sequential/SGD/functional + правила broadcasting) ≈ 1100–1500 |
| Главный минус | **Полный контракт torch — ловушка**: broadcasting, `Parameter`, in-place, `no_grad`, семантика `retain_graph` либо дорого эмулировать, либо «похоже, но врёт» — для образовательного продукта расхождение-обманку хуже отсутствия. А главного потребителя (студенческого кода) в v1 нет |

### 5.3 Вердикт

**Целиком — пере-инжиниринг для Фазы 2. Подмножество — да**: `requiresGrad`, `zeroGrad()`, класс `SGD` с `step()` (шаг update в трейсе уже есть как фаза «update», формула `W = W − η·∂L/∂W`), функциональные лоссы `F.bce/F.ce`, имена методов torch. Module/Sequential отложить до R2-playground.

## 6. Вариант D — дуальный режим: «обучающий» + «быстрый»

### 6.1 Суть

Один движок, режимы задаются **recorder-стратегией**, а не вторым движком:

```ts
const run = new TrainingRun(scenario)
const trace = run.buildTrace()                    // teaching: каждый op → TraceStep
const stats = run.runEpochs(n, { trace: false })  // fast: те же ops, запись выключена,
                                                  // агрегируются только loss по сэмплам
// детерминизм-тест: fast.losses[k] === значениям, полученным в teaching-режиме
```

### 6.2 Оценка

- **Минимум D неизбежен уже в Фазе 3:** MNIST-walkthrough с макро-шагами «эпоха N» требует прогнать все сэмплы предыдущих эпох — без записи (иначе память и время). То есть вопрос не «нужен ли D», а «сколько D строить сейчас».
- **Риск расхождения чисел** между режимами купируется тем, что ops одни и те же функции, различается только запись; детерминизм-тест сравнивает оба пути (дёшево, в Vitest).
- **Перф:** fast-режим без записи — эпохи MNIST тривиальны (десятки мс). Батчинг/векторизация мини-батчей в v1 не нужны — это уже настоящий over-engineering.
- **Объём:** +100–200 LOC, если заложить интерфейс recorder сразу; retrofit дороже и кривее (придётся выковыривать запись из ops).

### 6.3 Вердикт

**Принять как тонкий срез:** интерфейс recorder + флаг `trace: false` закладываются в Фазе 2 (когда ops всё равно пишутся), полный fast-режим с батчами — Фаза 3+/R2.

## 8. Рекомендация: гибрид «B-каркас + C-подмножество + D-флаг»

### 8.1 Что взять от micrograd

1. **Механику графа**: узлы с `_backward`-замыканиями, topo-сортировка, аккумуляция `grad` — построчный порт уже проверенного `gen_mock_trace.py` (включая gradcheck в Vitest с дня один).
2. **Порядок суммирования** — фиксируется ядром и зеркалится в скалярном экспандере (инвариант Р-1 становится тестируемым).
3. **Скалярный Value-уровень** — как ленивый drill-down-экспандер (view-слой, не путь исполнения).
4. `gen_mock_trace.py` остаётся эталоном скалярных чисел для фикстур второго уровня.

### 8.2 Что взять от PyTorch

1. **Имена методов**: `matmul/add/tanh/sigmoid/sub/pow`, `backward()`, `zeroGrad()` (camelCase — см. §8.4).
2. **Семантику аккумуляции градиента** и оптимизатор: `class SGD { step(); zeroGrad() }` — шаг update трейса становится honest PyTorch-паттерном.
3. **`requiresGrad`** — явно маркирует параметры (входы/метки без него).
4. **Функциональные лоссы** `F.bce(pred, y)` + метод-дубликат `bce(target)` для цепочек.
5. `Float64Array` как хранилище (float64 ↔ `torch.float64`).

### 8.3 Чего не брать в v1 (анти-скоуп)

`Module`/`Sequential`/`Parameter`, broadcasting (у нас фиксированные формы: rank ≤ 2; bias-add — отдельная op-шаг, как в трейсе), in-place ops, `no_grad`/`detach`/`retain_graph`, n-мерные тензоры, мини-батчи. Все — до R2-playground/«train-your-own».

### 8.4 Микрорешения

- **camelCase vs snake_case:** `zeroGrad()` вместо `zero_grad()`. Имена всё равно распознаются 1:1, а ESLint/TS-конвенции не ломаем. Таблицу соответствия имён (`backward↔backward`, `zeroGrad↔zero_grad`, `matmul↔matmul`, `F.bce↔F.binary_cross_entropy`) зафиксировать в плане 02-01.
- **Ориентация:** `matmul` без неявных транспонирований; формула шага `z = W·x` ↔ `W.matmul(x)` ↔ `torch.matmul(W, x)`.
- **Эмит схемы:** трейс-билдер выдаёт `TraceStep` schemaVersion 1 — `src/player/types.ts` не меняется; поле `provenance` расширить структурированно (см. открытые вопросы).

### 8.5 Целевой скетч Фазы 2 (сигнатурный контракт)

```ts
// engine/tensor.ts — единственный класс данных
// engine/ops.ts    — forward/backward ядра + локальные производные для drill-down
// engine/sgd.ts    — SGD.step/zeroGrad
// trace/builder.ts — (Scenario) → RunTrace, recorder-стратегия (teaching/fast)

const x = Tensor.of(sample.x)                       // requiresGrad = false
const [W1, b1, W2, b2] = paramsFromScenario(scn)    // requiresGrad = true
const L = W1.matmul(x).add(b1).tanh().matmul(W2).add(b2).sigmoid().bce(y)
L.backward()                                        // micrograd-механика
opt.step(); opt.zeroGrad()                          // PyTorch-паттерн
```

## 9. Риск пере-инжиниринга — честная оценка

- Фаза 2 = движок + XOR-MVP. Гибрид §8 — right-sized: ~700–900 LOC с provenance, ноль зависимостей, без Module-инфраструктуры.
- **Полный C — пере-инжиниринг сейчас**: его главный потребитель (студенческий код) появится в R2; строить API под несуществующий экран — нарушать собственный принцип «content iteration without touching verified numerics» в обратную сторону.
- **D целиком (батчи, векторизация эпох) — пере-инжиниринг**: закладывается только recorder-интерфейс (~десятки LOC), пока ops пишутся.
- **A как движок — ложная экономия**: меньше кода сегодня, но MNIST-перф и отсутствие тензорного API гарантируют переписывание в Фазе 3.
- Контрольный предохранитель: если движок (без provenance/tests) выходит за ~600 LOC или в нём появляется больше одного класса данных — сигнал, что ползём в C.
