# Pitfalls Research

**Domain:** Минимальный React 19 SPA (без роутера/state-библиотек, JS без TS) + agent-driven development (Claude Code под permissions/hooks/GSD) — стенд для отладки агентной инфраструктуры
**Researched:** 2026-10-23
**Confidence:** HIGH (проверено на живом коде репозитория: `npm run lint`/`npx eslint`, конфиги Vitest/Playwright/ESLint, hooks в `.claude/settings.json`)

Контекст milestone: пост-логин страница-дашборд + инлайн-валидация формы логина. Pitfalls охватывают обе плоскости: React-специфику и специфику работы агента в этом репозитории (hooks, permissions, тестовые раннеры).

## Critical Pitfalls

### Pitfall 1: `npm run lint` не линтит `.jsx`-файлы — ложнозелёный линт

**What goes wrong:**
Скрипт `"lint": "eslint ."` без `--ext` линтит только `.js`. Все компоненты проекта — `.jsx`, т.е. `npm run lint` их **не проверяет**. Проверено на текущем коде: `npm run lint` выходит 0 без вывода, при этом `npx eslint src/pages/LoginPage.jsx` даёт 2 ошибки (`jsx-a11y/label-has-associated-control`, строки 24 и 32) и 1 warning (`no-console`). Журнал `docs/memory.md` записал «lint зелёный» — это ложное подтверждение.

**Why it happens:**
ESLint 8 при передаче каталога линтит только `.js` по умолчанию. Проект перешёл на airbnb с jsx-a11y, но скрипт остался от JS-каркаса. PostToolUse-хук `eslint --fix "$f" ... || true` линтит отдельные файлы правильно, но глотает все неавтофиксируемые ошибки (`|| true`), так что и хук об этом не сообщает.

**How to avoid:**
- Поправить скрипт: `"lint": "eslint . --ext .js,.jsx"` (миграция на flat config `eslint.config.js` тоже решает — там `eslint .` линтит всё, но это больше работы).
- Считать `npm run lint` (после фикса) единственным источником правды; хук — только автофиксер.
- В верификации каждой фазы требовать file-level `npx eslint <изменённые файлы>` или исправленный скрипт.

**Warning signs:**
- `npx eslint <файл>` показывает ошибки сразу после зелёного `npm run lint`.
- Вывод `npm run lint` пустой, хотя менялись только `.jsx`.
- Новые ошибки jsx-a11y «не замечаются» до ревью.

**Phase to address:**
Tooling-фаза (перед работой над компонентами) — это блокер: без него верификация «lint green» в каждой следующей фазе фиктивна.

### Pitfall 2: Паттерн `<label htmlFor>` + sibling `<input>` валит jsx-a11y — и это не автофиксится

**What goes wrong:**
Текущий паттерн `LoginPage.jsx` (label и input — соседи по JSX, связаны через `htmlFor`/`id`) даёт `jsx-a11y/label-has-associated-control` error при file-level линте. `eslint --fix` это не чинит. Агент скопирует паттерн в форму дашборда/валидации → +N неавтофиксируемых ошибок, невидимых для `npm run lint` (см. Pitfall 1).

**Why it happens:**
Правило по умолчанию не резолвит связку htmlFor→id у разнесённых siblings — классическая боль airbnb+jsx-a11y. Хук `--fix` с `|| true` скрывает проблему, а агент не смотрит вывод хука.

**How to avoid:**
- Один раз принять проектный паттерн и зафиксировать: либо вкладывать `<label>Текст<input .../></label>` (проще, плюс увеличивает зону клика), либо настроить `jsx-a11y/label-has-associated-control: ['error', { assert: 'htmlFor' }]` и проверить, что текущая разметка проходит.
- В паттерн сразу включать связку ошибки с полем: `aria-invalid` + `aria-describedby` на input — это заодно закрывает UX/a11y-часть инлайн-валидации.

**Warning signs:**
- Новый компонент с формой скопирован из LoginPage.
- `npx eslint src/pages/*.jsx` красный после «чистой» записи файла.

**Phase to address:**
Design/Tooling-фаза — решение о паттерне до имплементации; верификация в фазе имплементации.

### Pitfall 3: Переключение страниц без роутера — дрейф дизайна состояния в `App.jsx`

**What goes wrong:**
Роутера нет (и не будет — стек зафиксирован), значит переход «логин → дашборд» — это условный рендер по `useState` в `App.jsx`. Типичные ошибки: (а) агент предлагает react-router / hash-роутинг «как положено» — нарушение зафиксированного стека; (б) состояние входа размазывается по компонентам или дублируется; (в) агент кладёт `loggedIn` в `localStorage` «чтобы дашборд выживал при обновлении» — появляется квази-аутентификация, которой в Out of Scope нет; (г) дашборд рисуется через `display: none` рядом с логином — оба в DOM, тесты по `getByLabelText` ловят дубли.

**Why it happens:**
Агенты натренированы на «правильные» решения больших приложений (роутер, персистентность) и неохотно пишут намеренно «наивный» код. Тестовая задача (стенд) требует минимализма, а не best practice.

**How to avoid:**
- Зафиксировать в спеке фазы дизайн заранее: `App.jsx` держит `const [user, setUser] = useState(null)`; `LoginPage` получает колбэк `onLogin(email)`; `user ? <Dashboard/> : <LoginPage/>` — unmount логина автоматически чистит состояние полей.
- Явно записать: обновление страницы возвращает на логин — это принимаемое поведение заглушки, не баг.
- Запретить `localStorage`/`window.location` для этой задачи — они не нужны.

**Warning signs:**
- В плане/диффах появляются `react-router`, `hashchange`, `window.location`, `localStorage`.
- Условие `{user && <Dashboard />}` соседствует с всегда-смонтированным `<LoginPage />`.

**Phase to address:**
Planning/Spec-фаза — дизайн состояния утверждается до кода.

### Pitfall 4: E2E ломаются молча при переходе на по-полевую валидацию (strict mode + `toBeHidden`)

**What goes wrong:**
Сейчас селектор `getByRole('alert')` уникален — одна общая ошибка. Инлайн-валидация по требованиям (`Ошибки ... показываются инлайн`) почти неизбежно ведёт к **нескольким** `role="alert"` (email + пароль) → `page.getByRole('alert')` падает по strict mode violation, `screen.getByRole('alert')` в Testing Library кидает "multiple elements". Хуже обратное: тест «заполненная форма отправляется без предупреждения» использует `toBeHidden()`, который проходит и когда элемента нет, и когда он есть, но `visibility: hidden` — ложнозелёный после любых CSS-правок.

**Why it happens:**
Селекторы писались под одну ошибку; рефакторинг валидации меняет DOM-контракт, а тесты «допиливаются на ходу» до зелени вместо пересмотра контракта.

**How to avoid:**
- При редизайне валидации обновлять селекторы осознанно, как часть задачи: скопировать ошибки (`page.getByText('...')` с уникальными текстами), для отсутствия использовать `toHaveCount(0)`, а не `toBeHidden()`.
- Сообщение об ошибке — мини-контракт: тексты полей («Введите email», «Введите пароль») фиксируются на этапе дизайна, тесты обновляются пачкой.
- Пограничный случай: общая ошибка уже показана, пользователь снова сабмитит — `role="alert"` не реанонсируется скринридером, если узел не пересоздан; проверить `key`/условие рендера.

**Warning signs:**
- "strict mode violation: getByRole('alert') resolved to N elements".
- Тест молча проходит при сломанном UI.
- В новых тестах `page.waitForTimeout(...)` вместо `await expect(...)`.

**Phase to address:**
Test-design внутри фазы имплементации валидации; верификация — e2e-фаза.

### Pitfall 5: Разрыв покрытия: переход логин→дашборд не протестирован

**What goes wrong:**
Юниты тестируют `LoginPage` и `Dashboard` изолированно, e2e — только форму. Сам переход (состояние в `App.jsx`, колбэк `onLogin`, условный рендер) остаётся без тестов — ровно та логика, которая добавляется в этом milestone. Требование «новые фичи покрыты юнит-тестами и e2e» формально выполнено, фактически нет.

**Why it happens:**
Тесты пишутся per-component по привычке; состояние в App — «просто связка», которую никто не тестирует. У агента нет причины добавить App-level интерактивный тест, если фаза этого явно не требует.

**How to avoid:**
- В план тестов явно включить: юнит на `App` (заполнить форму → сабмит → появился заголовок дашборда, логин исчез) + e2e полный флоу (goto → fill → submit → assert dashboard).
- Критерий готовности фазы: «переход покрыт и юнитом, и e2e», не «у каждого компонента есть тест».

**Warning signs:**
- Новые тест-файлы только у новых компонентов; `App.test.jsx` не менялся.
- В e2e ни один тест не проходит полный путь входа.

**Phase to address:**
Фаза юнит-тестов + фаза e2e (обе должны содержать флоу-тест).

### Pitfall 6: Тесты, которые молча не запускаются (vitest include ограничен `src/**`)

**What goes wrong:**
`vite.config.js` включает только `src/**/*.test.{js,jsx}`. Новый юнит-тест, положенный в `e2e/` или другую директорию, **не выполняется вовсе** — `npm test` зелёный, количество тестов не изменилось, агент отчитывается «тесты зелёные». Вариант хуже: `.test.js` файл в `e2e/` подхватит Playwright и упадёт на этапе сборки непонятным образом.

**Why it happens:**
Конвенция «юниты в src/, e2e в e2e/» известна, но агент без явной проверки не замечает, что его новый файл не попал в прогон.

**How to avoid:**
- После добавления теста сверять вывод `npm test`: файл должен появиться в списке прогонов Vitest и счётчик тестов должен вырасти.
- Юниты — только colocated в `src/`; e2e-спеки — только в `e2e/` и только с playwright-импортами.

**Warning signs:**
- `npm test` показывает то же число тестов, что до добавления файла.
- В выводе Vitest нет строки с новым файлом.

**Phase to address:**
Фаза юнит-тестов (критерий готовности: новый файл виден в прогоне).

### Pitfall 7: E2E против устаревшего dev-сервера (`reuseExistingServer: true` + порт 5174)

**What goes wrong:**
`playwright.config.js` использует `reuseExistingServer: true` и `baseURL: http://localhost:5173`. Если на 5173 висит старый vite-процесс из прошлой сессии (или от фонового `npm run dev` агента), e2e гоняются против **старого кода** — ложнозелёные или ложно-красные прогоны. Второй сценарий: старый сервер занял 5173, новый vite из webServer тихо сел на 5174, e2e стучатся на 5173 не в тот сервер.

**Why it happens:**
Агент запускал dev-сервер для chrome-devtools MCP, забыл остановить; либо у пользователя остался терминал. Vite молча инкрементирует порт. `reuseExistingServer` нужен для локального UX и не отличает «мой» сервер от чужого.

**How to avoid:**
- Перед e2e-прогоном после правок: проверить `lsof -ti:5173` и завершить чужой процесс, либо убедиться, что сервер стартовал в этой сессии.
- Хотя бы одно ручное подтверждение через chrome-devtools MCP (reload страницы + snapshot) после «зелёных» e2e при крупной правке.
- Опционально в конфиге: `port: 5173, strictPort: true` — тогда vite упадёт громко вместо тихого переезда на 5174.

**Warning signs:**
- e2e зелёные, но в MCP-бразере изменения не видны (нужен hard reload).
- Два vite-процесса в `ps`.
- Тест то проходит, то нет без изменений кода.

**Phase to address:**
Фаза e2e/верификации; `strictPort` — кандидат в tooling-фазу.

### Pitfall 8: PostToolUse `eslint --fix` конфликтует с агентом (stale file state, циклы правок)

**What goes wrong:**
Хук перезаписывает файл после каждого Write/Edit. Если хук что-то пофиксил, представление агента о файле расходится с диском → следующий `Edit` падает на `old_string` mismatch, либо агент откатывает «лишний» фикс и хук возвращает его обратно (микроцикл). Плюс `|| true` скрывает и ошибки хука, и неавтофиксируемые проблемы (см. Pitfall 1).

**Why it happens:**
Агент делает серию микро-правок по устаревшему снимку файла и не перечитывает его после хука; airbnb-стиль отличается от «естественного» стиля модели (кавычки, порядок, стрелочные).

**How to avoid:**
- Писать сразу в airbnb-стиле (правила проекта: стрелочные компоненты, шаблонные строки, деструктуризация, `const`).
- Одна согласованная правка файла вместо серии мелких; после конфликтного Edit — перечитать файл.
- Не «побеждать» хук: если `--fix` меняет код, это сигнал переписать исходную правку в стиле конфига.

**Warning signs:**
- Повторяющиеся ошибки `old_string` в одной сессии.
- Один и тот же участок файла меняется трижды подряд.

**Phase to address:**
Конвенция имплементации (все кодовые фазы); фикс в tooling-фазе — показать вывод хука агенту/в статусе вместо полного глушения.

### Pitfall 9: Scope creep через «полезность»: роутер, TS, state-библиотека, form-библиотека, prop-types

**What goes wrong:**
Агент, решая задачу «дашборд после логина», стандартно предлагает: react-router (нужна «страница»), react-hook-form (валидация), zustand (состояние), TypeScript «для надёжности», prop-types «по airbnb». Стек зафиксирован, `npm install` — ask-gated, поэтому либо план стопорится на подтверждении, либо агент городит самодельный аналог библиотеки (мини-роутер на hashchange) — хуже оригинальной задачи.

**Why it happens:**
Обучающий датасет агентов полон «правильных» боевых решений; намеренный минимализм стенда контринтуитивен и нигде в задаче фазы не повторяется.

**How to avoid:**
- В каждой фазовой спеке повторять ограничения явно: «без новых зависимостей, без роутера, без state-библиотек, JS без TS».
- Решение о любой новой зависимости — только явный вопрос пользователю, не workaround.

**Warning signs:**
- В плане фазы упомянуты внешние пакеты.
- В `src/` появляется собственный `router.js`/`events.js` общего назначения.

**Phase to address:**
Planning/Spec каждой фазы (ограничения — в преамбуле спеки).

### Pitfall 10: Эффекты данных дашборда без cleanup: StrictMode, setState после unmount, act-предупреждения

**What goes wrong:**
Дашборд по конвенции получает данные через `useEffect`. Если агент имитирует загрузку `setTimeout`/`Promise` без cleanup, при React 19 + `StrictMode` (двойной маунт в dev) получаем: setState на размонтированном компоненте, предупреждения `act(...)` в тестах, флаки. При переключении назад на логин (когда появится logout) — утечки таймеров.

**Why it happens:**
Для «заглушки без бэкенда» эффект кажется тривиальным; очистка воспринимается как over-engineering, а правило проекта требует её явно.

**How to avoid:**
- Любой эффект: `useEffect` с cleanup (`clearTimeout`, отмена `Promise` через флаг/`AbortController`) или кастомный хук `useDashboardData`.
- В юнит-тестах на асинхронность — `userEvent`/`findBy*`, при таймерах — fake timers.

**Warning signs:**
- `Warning: An update to ... inside a test was not wrapped in act(...)`.
- `Can't perform a React state update on an unmounted component`.
- `useEffect` без return-функции рядом с setTimeout/подпиской.

**Phase to address:**
Фаза имплементации дашборда (design review эффекта до кода).

### Pitfall 11: Смешение агентной инфраструктуры с кодом приложения в коммитах

**What goes wrong:**
Сейчас в рабочем дереве десятки untracked-файлов `.claude/gsd-*`, `.claude/hooks/*`, `.planning/*`. Коммит milestone «дашборд + валидация», сделанный `git add .`, утянет всю инфраструктуру GSD — история неделима, откат фичи тянет за собой инфраструктуру, а стенд как раз учит наблюдаемости шагов агента.

**Why it happens:**
`git add *`/`git commit -am` разрешены allow-правилами; агенты экономят ходы и не сортируют файлы по смысловым группам.

**How to avoid:**
- Раздельные коммиты: `agent infra: ...` для `.claude/**`/`.planning/**`, фичевые — для `src/**`/`e2e/**`.
- Один раз решить и зафиксировать в Key Decisions, версионируются ли GSD-файлы вообще (сейчас они untracked — состояние уже «решилось само», надо закрепить).

**Warning signs:**
- `git status` перед коммитом содержит файлы из `.claude/` вместе с `src/`.
- Коммит меняет >5 файлов в обеих зонах сразу.

**Phase to address:**
Гигиена коммитов на каждой фазе (правило в чек-листе завершения фазы).

### Pitfall 12: `console.log` остаётся в коде валидации (и пароль рискует попасть в лог)

**What goes wrong:**
В `LoginPage.jsx` уже есть `console.log('login', { email })` (warning `no-console`). При доработке валидации агент усложняет логирование и легко добавляет `{ email, password }` — кред в консоли браузера. Уровень ошибки разный: warning vs утечка, но корень один — «временный» лог «для отладки агента» остаётся навсегда.

**Why it happens:**
Модель использует console.log как инструмент наблюдаемости при отладке и не всегда убирает за собой; `no-console` в airbnb — warning, не error, и не попадает в «красный» статус.

**How to avoid:**
- Правило фазы: в коде фичи — ноль `console.*`; отладочный вывод удаляется до коммита.
- Никогда не логировать и не хранить значение пароля (ни в state дашборда, ни в localStorage, ни в data-атрибутах).

**Warning signs:**
- `grep -rn "console\." src/` перед коммитом непустой.
- В объекте лога рядом с email упоминается password.

**Phase to address:**
Фаза имплементации + чек-лист завершения фазы.

## Technical Debt Patterns

| Shortcut | Immediate Benefit | Long-term Cost | When Acceptable |
|----------|-------------------|----------------|-----------------|
| Оставить `eslint .` без `--ext` | не трогать работающий скрипт | jsx-файлы без линта; копятся неавтофиксируемые ошибки (уже есть 2) | никогда — фикс в одну строку |
| `console.log` как наблюдаемость агента | быстрый дебаг | warning no-console, риск залогировать креды | только в сессии отладки, удалять до коммита |
| `toBeHidden()` для проверки отсутствия ошибки | тест проходит сразу | ложнозелёный при visibility-скрытии | никогда в новых тестах — использовать `toHaveCount(0)` |
| `localStorage` для «выживания» дашборда при F5 | выглядит удобнее | квази-аутентификация вне scope, рассинхрон с тестами | никогда для этого milestone |
| Самодельный hash-роутер «на 20 строк» | избежать ask на react-router | скрытая зависимость, несовместимая с зафиксированным стеком | никогда — лучше честный вопрос пользователю |
| Обновлять сломанные тесты «под новый код» до зелени без ревизии контракта | быстрая зелёная сборка | тесты подтверждают реализацию, а не требования | никогда; сначала зафиксировать новый контракт (тексты, селекторы) |
| Коммит `git add .` (инфра + код вместе) | экономия ходов агента | неделимая история, откат фичи тянет GSD-файлы | никогда — раздельные коммиты |

## Integration Gotchas

| Integration | Common Mistake | Correct Approach |
|-------------|----------------|------------------|
| PostToolUse-хук `eslint --fix` | Доверять хуку как проверке; не замечать `|| true` | Хук — только автофиксер; истина — `npm run lint` (после добавления `--ext .js,.jsx`) и file-level `npx eslint <файл>` |
| PreToolUse-хук protect-paths / deny `.env` | Пытаться «обойти» чтение `.env` через `cat`/grep из Bash | Хук и deny — часть стенда; не обходить, не тестировать на обход в фичевых фазах |
| Playwright `webServer` (`reuseExistingServer: true`) | Гонять e2e против старого/чужого сервера на 5173 | Перед прогоном проверить владение портом; кандидат: `strictPort: true` |
| chrome-devtools MCP браузер | Сверять e2e-результат в MCP-браузере с закешированной страницей (без reload) | Hard reload + свежий snapshot; MCP-браузер и Playwright — разные контексты, состояние не делится |
| Vitest include `src/**` | Класть юнит-тесты вне `src/` — они молча не запускаются | Colocated `*.test.jsx` в `src/`; проверять файл в выводе прогона |
| GSD-субагенты | Предполагать, что субагент видит `docs/memory.md`-контекст родителя | Журнал обновляет ведущий агент в конце сессии; фазовые спецификации — самодостаточны |
| `npm install` (ask) | Планировать фазу с новой зависимостью без явного решения пользователя | Все фазы — в рамках текущих deps; новая dep — отдельное решение до планирования |

## Performance Traps

Проект — тестовый стенд, пороги «масштаба» здесь не про пользователей, а про устойчивость агентного цикла.

| Trap | Symptoms | Prevention | When It Breaks |
|------|----------|------------|----------------|
| Два vite-сервера (старый на 5173, новый на 5174) | e2e бьют в старый код; MCP-браузер — в новый; результаты противоречивы | `strictPort: true`; проверка `lsof -ti:5173` перед e2e | С первой же фоновой сессии `npm run dev` |
| StrictMode двойной маунт эффектов | act-предупреждения, двойные fetch/setTimeout в dev | useEffect с cleanup; тесты через `findBy*`/fake timers | Как только у дашборда появляется асинхронность |
| Флаки e2e на таймингах (`waitForTimeout`) | Тесты то зелёные, то красные без изменения кода | Только `await expect(...).toBe*()` / `toHave*()` авто-wait утверждения | Уже при 3–5 e2e-сценариях |
| HMR-состояние долгоживущей dev-сессии | В браузере «странное» состояние после серии правок агента | Перед финальной e2e-верификацией — reload страницы | Длинные сессии с 10+ правками подряд |

## Security Mistakes

Реального бэкенда нет, поэтому риски — репутационно-гигиенические для стенда.

| Mistake | Risk | Prevention |
|---------|------|------------|
| `console.log` с password в форме/дашборде | Кред в консоли браузера, попадает в скриншоты документации (`docs/assets/`) | Логировать только email; правило «ноль console.* в фичевом коде» |
| `localStorage` с «токеном»/кредами для персистентности входа | Появляется видимость реальной аутентификации вне Out of Scope; шаблон утечёт в реальные проекты | Не персистировать ничего авторизационного; F5 → логин — принятое поведение |
| Скриншоты e2e/дебага в коммит с чувствительными данными | Утечка через публичный репозиторий учебного проекта | Скриншоты только в `docs/assets/`, с тестовыми данными (`user@example.com`) |
| Попытки читать `.env` «в исследовательских целях» | Нарушение модели стенда, триггер deny-правил | `.env` не трогать вовсе; в фичевых фазах он не нужен |

## UX Pitfalls

| Pitfall | User Impact | Better Approach |
|---------|-------------|-----------------|
| Ошибка валидации не исчезает при вводе | Пользователь исправил поле, ошибка висит и вводит в заблуждение | Сбрасывать ошибку поля при `onChange` (или ре-валидировать на submit) |
| Одна общая ошибка вместо по-полевой при инлайн-валидации | Непонятно, какое поле заполнять | Per-field `role="alert"`/`aria-describedby`, `aria-invalid` на input |
| Ошибка анонсируется скринридером один раз и не обновляется при повторном сабмите | Пользователь с AT не узнаёт, что ошибка вернулась | Пересоздавать узел (key) или использовать `aria-live`-семантику осознанно |
| Фокус не управляется после перехода на дашборд | AT-пользователь остаётся «в пустоте» | Заголовок дашборда — `h1`, при маунте можно сфокусировать main (проверить jsx-a11y) |
| `noValidate` убран вместе с рефакторингом | Браузерный tooltip валидации `type="email"` дублирует/перекрывает инлайн-ошибки | Сохранить `noValidate` — валидация только наша, предсказуемая для тестов |

## "Looks Done But Isn't" Checklist

- [ ] **Дашборд:** часто нет теста на переход (логин→дашборд) — проверить, что есть и App-level юнит, и полный e2e-флоу.
- [ ] **Дашборд:** не проверено поведение при F5 (должен возвращаться на логин — принять и зафиксировать, не «чинить»).
- [ ] **Инлайн-валидация:** часто нет сброса ошибки при вводе — проверить вручную и тестом (тип → ошибка исчезла).
- [ ] **Инлайн-валидация:** часто нет связки с полем (`aria-describedby`/`aria-invalid`) — проверить файл-level `npx eslint`.
- [ ] **Тесты:** новый файл часто молча не в прогоне — проверить, что Vitest-вывод содержит его и счётчик вырос.
- [ ] **Линт:** `npm run lint` зелёный, но jsx не проверялся — проверить `npx eslint . --ext .js,.jsx` до и после фикса скрипта.
- [ ] **Валидация:** `toBeHidden()`-тесты остались — заменить на `toHaveCount(0)`.
- [ ] **Гигиена:** `grep -rn "console\." src/` пуст; коммиты разделены (инфра vs код); `docs/memory.md` дописан в конце сессии.

## Recovery Strategies

| Pitfall | Recovery Cost | Recovery Steps |
|---------|---------------|----------------|
| Ложнозелёный `npm run lint` (без --ext) | LOW | Добавить `--ext .js,.jsx`, прогнать, зафиксить накопленные ошибки (2 сейчас), ужесточить чек-лист фазы |
| Множественные `role="alert"` ломают селекторы | LOW | Уникализировать тексты ошибок, обновить селекторы тестов пачкой, заменить `toBeHidden` → `toHaveCount(0)` |
| `localStorage`/самодельный роутер уже вкоде | MEDIUM | Откатить к `useState` в App; обновить тесты; записать решение в Key Decisions, чтобы не повторилось |
| E2e-тесты против старого сервера | LOW | Убить процесс на 5173, перезапустить прогон; включить `strictPort: true` |
| Тест-файл вне `src/` не запускался | LOW | Перенести в `src/` (colocated), убедиться, что файл в выводе Vitest |
| setState после unmount / act-предупреждения | LOW | Добавить cleanup в эффект, `findBy*` в тестах |
| Инфра+код в одном коммите | MEDIUM | `git reset --soft HEAD~1`, разделить на два коммита (пока не запушено; push — ask) |
| `docs/memory.md` не дописан | LOW | Дописать строку в следующей сессии; держать правило в чек-листе конца фазы |
